# S2: Can the Twilight Forest generate its own chunks on Bedrock, deterministically and Java-exact, inside the custom dimension?

| | |
|---|---|
| Unit | F5 |
| Status | answered with a fallback (server-side custom biomes yes; client biome visuals need the client mod) |
| Date | 2026-11-02 |
| Game / LeviLamina | 1.26.51 / 26.51.7 |

## Question

Can a mod-owned `WorldGenerator` produce every chunk of `twilightforest:twilight_forest` through a staged
pipeline (biomes, starts, noise, surface, carvers, features, pieces, blankets, spawns) on the engine's
generation worker threads, with the same random numbers and noise values as TF 4.8 on Java 1.21.1, and can
the chunks carry TF's custom biomes (server biomes, the client's view of them, spawn rules, map colours)?

## Why it matters

Everything world-shaped in TF depends on it: U1 (biome source, the 22 biomes), U2 (terrain, carvers, blankets),
U3 (trees), U18/U19 and every landmark unit (features, pieces, controlled spawns), U16/U17 (natural spawning),
U13 (maps). Parity of terrain and decoration needs bit-exact Java random sources and noises, Java's seeding of
every placed feature (`WorldgenRandom#setFeatureSeed(decorationSeed, featureIndex, step)` over FeatureSorter's
order) and of every carver (`setLargeFeatureSeed(seed + index, sourceX, sourceZ)`).

## What was tried

1. **Java-parity core** (`src/core/jrand`, `src/core/noise`, pure C++): LegacyRandom (java.util.Random /
   LegacyRandomSource), Xoroshiro128++ (`RandomSupport` seeding, MD5 `fromHashOf`), WorldgenRandom (decoration,
   feature, large-feature, salted and slime seeds), positional factories, `Mth#getSeed`, String#hashCode,
   ImprovedNoise, SimplexNoise, PerlinNoise (modern and legacy), NormalNoise, PerlinSimplexNoise, the vanilla
   density functions with cubic splines (float maths as Java), NoiseChunk interpolation (`interpolated`,
   `flat_cache`), FeatureSorter, `HashSet<BlockPos>` iteration order and `Mth#sin`. All floating point code is
   compiled with `#pragma clang fp contract(off)` (no FMA), so it rounds like the JVM.
2. **Java oracle**: `tests/worldgen/oracle/Oracle.java` runs against the Minecraft 1.21.1 server jar (official
   mappings, reflection) and prints 103 sample lines; `tests/worldgen/JavaParityTest.cpp` rebuilds every line in
   C++ and compares them character for character (doubles by raw bits).
3. **Generator** (`src/feature/worldgen/Generator.cpp`): `TwilightGenerator : VoidGenerator` (MCAPI constructor
   `VoidGenerator(Dimension&, BiomeIdType)`), overriding `loadChunk` (Biomes .. Carvers into the `LevelChunk`
   through `setBlockSimple` / `_setBiome`, then `recomputeHeightMap` and `tryChangeState(Generating, Generated)`)
   and `decorationPostProcessChunk` (a `BlockSource` over the `ChunkViewSource` neighbourhood = Java's
   WorldGenRegion; the center chunk found from the view's bounds and checked by its `DecorationPostProcessing`
   state). It is installed by hooking `CustomDimension::$createGenerator` (MCAPI) for the dimension named
   `twilightforest:twilight_forest`, so it does not depend on how F4 registers the dimension;
   `gf::worldgen::ext::createGenerator(Dimension&)` hands it to any other backend.
4. **Carvers** as `ChunkGenerator#applyCarvers`: for the chunk C being carved, every source chunk S within 8
   chunks (17 x 17) gives the carvers of its biome (the biome source at S's minimum block, quart y 0; cached per
   source chunk across the worker threads), and the carver at index k of that list runs once with
   `setLargeFeatureSeed(seed + k, S.x, S.z)`. The carver tests `isStartChunk` itself (TF's highland caves
   override it) and gets S, k, its configured carver JSON and C's carving mask through
   `gf::worldgen::ext::carverContext()` (`src/feature/ext/worldgen/Carving.h`).
5. **Feature interpreter** (`src/feature/features`): configured / placed features from the imported data
   (`<mod>/data/<ns>/worldgen/**`), Java's lazy placement streams reproduced depth first, 17 vanilla feature types
   (ore and scattered_ore separately), 20 placement modifiers (with TF's `no_structure` and `chunk_centerer`), the
   providers / predicates / rule tests, the tree feature with vanilla trunk / foliage placers, feature sizes and
   decorators (decorators get Java's `HashSet` order), the 26 vanilla placed features TF's biomes reference
   (values from the vanilla data generator) and LargeWriter (queued blocks, drained by the chunk's own
   decoration or, for chunks already finished, on the server thread; persisted in the world DB). Block tags:
   the built-in vanilla members, gf::tags, and the imported tag JSON itself (`<mod>/data/<ns>/tags/block`).
   The decoration biomes are collected per chunk by engine biome pointer (named once, cached).
6. **Custom biomes**: the generator writes biome ids per quart (column fill when uniform) through
   `LevelChunk::_setBiome` with `BiomeRegistry::lookupByName`; ids without a namespace are vanilla
   ("minecraft:plains" <-> "plains"), custom ids keep theirs. The probe: the worldgen e2e scenarios install a
   behavior pack biome `gf_test:worldgen_probe` (format 1.21.110, `minecraft:climate` temperature 2.0, downfall
   0.0) into the deployed copy of the test pack before the world loads (`worldgen.prelaunch.ps1`), and on the
   client a resource pack look for it (`biomes_client.json`: magenta water, `fog_identifier` with a magenta air
   fog). `worldgen.custom_biome` writes it into a live chunk and reads it back through the chunk and the block
   source; in the client scenario it paints chunks 3000 blocks away that the client has never received (loaded
   on the server by the test's simulated player), the player travels there, and
   `worldgen.custom_biome_restore` logs which biome the client's own level holds under the player and whether
   the client's biome registry knows the probe. `worldgen.generator` (with the dimension) uses the probe as the
   biome source, so the generator itself writes the custom id into new chunks.
7. **Spawns**: per-biome tables (registered, else the imported biome JSON; read under a shared lock, published
   with `try_emplace`), chunk-generation spawns (`NaturalSpawner#spawnMobsForChunkGeneration` with the spawn-box
   collision check and the WorldGenRegion random for the placement predicates), the natural spawner with Java's
   mob caps (no monsters on Peaceful), TF's `gatherPotentialSpawns` (piece spawn indices, the hollow hill dome,
   conquered starts) and the structures' spawn overrides (`ChunkGenerator#getMobsAt`).
8. **Functions**: `dev_new_world` / `dev_powerwash_chunk` as Bedrock functions in the mod's behavior pack, run
   with `/function twilightforest/...`; the TF-only half of `dev_new_world` (tfEnforcedProgression, the
   teleport into the Twilight Forest) goes through `scriptevent twilightforest:dev_new_world`, answered by a hook
   on `ScriptEventCommand::$execute` (MCAPI).

## Evidence

- gtest: `JavaParityTest` 103/103 oracle lines identical (random sources incl. gaussians, WorldgenRandom seeds,
  positional factories, getSeed, hashes, StrictMath.log, ImprovedNoise, Simplex 2D/3D, Perlin modern + legacy,
  NormalNoise, keyed RandomState noise, HashSet order, Mth.sin/cos, PerlinSimplex), `DensityTest` (density
  functions, splines, NoiseChunk corners / trilinear interpolation / flat_cache, FeatureSorter). Finding:
  Minecraft's gaussian uses `Math.log` (HotSpot intrinsic), which differs from `StrictMath.log` in the last bit
  for some inputs; the C runtime's `log` matches the JVM on every golden.
- Selftests `worldgen.*` (15, server and client builds): `java_parity`, `fixture_feature` (gf_test:fixture_column
  placed in memory with a fixed seed: the same golden hash on both builds, and placed in the world through a
  BlockSource region), `vanilla_features`, `tree`, `scattered_ore`, `large_writer`, `biomes`, `custom_biome`,
  `custom_biome_restore`, `carvers` (288 carver calls from 144 carver-biome source chunks around a chunk whose
  own biome has no carvers, each seed checked against `setLargeFeatureSeed(seed + index, x, z)`, the index
  counting an unregistered carver, one mask per chunk), `spawn`, `spawn_rules` (dome, overrides, piece indices,
  concurrent table lookups from 4 threads), `functions` (both functions run through `/function`: the cleared
  blocks, the kept ones, the 8 gamerules, the scriptevent answered; the rules are restored), `timing`,
  `generator`.
- Custom biome: BDS registers `gf_test:worldgen_probe` from the behavior pack without an experiment and without a
  content-log error; `worldgen custom biome: gf_test:worldgen_probe written and read back (was minecraft:plains)`
  (server and client builds). Client (local world, client build): the client's biome registry knows the probe
  (`probe in the client registry: true`), but chunks the server sent after painting arrive in the client's
  level as `minecraft:plains` (`the client level has minecraft:plains under its player`), and
  `custom_biome.png` shows ordinary plains (no probe fog or water colour). The same happened for chunks sent
  again after a trip away and back. So the server-side biome of a chunk does not reach the client's chunk for a
  pack-defined custom biome on this game version.
- In-dimension run (f4-dimension 362386c merged locally into this branch, not pushed; `-Scenario worldgen`
  exit 0, 15/15): the generator hook installed the Twilight generator, `worldgen.generator` loaded far chunks
  in the dimension, `worldgen generator: in-dimension run: 489 chunks generated (0.732 ms each), 257 decorated
  (0.008 ms each)`, and the generated chunk carried the custom biome from the biome source
  (`worldgen generator: generated chunk biome gf_test:worldgen_probe`). `dev_new_world` run by a player sent it
  to the Twilight Forest at x * 8, y 128, z * 8 (`gf_test_4 -> Twilight Forest 444.0 128 932.0`).
- Timing: `worldgen.timing` runs the whole pipeline on 200 chunks in memory and logs
  `worldgen timing: 200 chunks in <ms> ms (<ms>/chunk ...)`: `129.2 ms (0.65 ms/chunk, budget 50 ms/chunk)` on
  the BDS e2e slot (server build, release, shared machine). This is the framework baseline (fallback ground, no
  biome data, empty decoration loop); the in-dimension line above is the engine's real loadChunk / decoration
  cost with the same providers. U2 / A1 track the budget with TF's terrain and features (risk list).
- Determinism goldens pinned in the selftests and reproduced by the server and the client build: fixture feature
  `f3df82a014e6dc38`, vanilla features `172b5e4895dfc424`, vanilla tree `e7cec96b2660fb67`, 200-chunk pipeline
  `c6c6039616b07c4d` (in-memory worlds hashed by block id and permutation).
- e2e: `tools/e2e/server/run.ps1 -Scenario worldgen` exit 0 (`SELFTEST DONE pass=15 fail=0`), `-Scenario full`
  exit 0, the client scenario in `-Mode local`.

## Conclusion

Yes, with the CustomDimension route: the engine accepts a mod generator for a custom dimension
(`CustomDimension::mGeneratorCreator` / `$createGenerator`), loadChunk and decoration post-processing give the
two halves of Java's ChunkStatus pipeline (single chunk, then a 3x3 neighbourhood through a BlockSource), and the
core reproduces Java's numbers bit for bit, so seeds give TF's choices.

Custom biomes on the server: yes. A behavior pack biome with a namespaced id registers on BDS 1.26.51 (custom
biome id from `BiomeRegistry::mNextCustomBiomeId`, no experiment), the generator writes it into chunks before
they are sent, and everything server side (features' biome filters, spawn tables, temperature, the biome
source) sees it. Custom biomes on the client: not through the chunk data. The client's registry knows the
biome, but the client's copy of a chunk holds `minecraft:plains` where the server's holds the custom id, so the
client never draws a custom biome's pack look by itself. Routes for the rest of the biome feature set:
- Server biomes: U1 ships the 22 TF biomes as behavior pack biome JSON (climate from TF's temperature / downfall)
  and sets the biome source; the generator writes them.
- Client visuals (client mod): the companion protocol sends the client the TF biome of the chunks around the
  player (or the client mod runs U1's deterministic biome source with the world seed), and F12's
  `client.world` sky / fog / water / foliage providers draw TF's biome effects from it (U15 atmosphere, U1);
  the resource pack's client biome definitions stay for completeness. Follow-up for F12 / U1: a client-side
  write of the received biome into the client's chunk (`LevelChunk::_setBiome` on the client level), which
  would make Bedrock's own tinting work too.
- Vanilla clients: best effort; they see the chunk's vanilla fallback biome (plains here). U1 should give each
  TF biome a vanilla-looking fallback where it matters.
- Spawn rules: TF's mobs spawn from F5's spawner reading the biome JSON spawners (biome tags without vanilla
  spawn-rule tags, so Bedrock's own spawner does not add vanilla mobs).
- Map colours: map pixels are computed on the server, which has the custom biome (Bedrock tints grass, foliage
  and water pixels from the chunk's biome; not measured here); TF's magic and maze maps draw biome colours
  from the `magic_map_color` data map (U13), independent of the engine biome.

Limits: the providers run on worker threads and must only touch the chunk / region they get. Interleaving of
structure pieces is approximated (the Pieces stage runs at the surface-structures step). Bedrock vines have no
"up" face and leaves no distance property, so those Java states collapse; Bedrock grass has no "snowy" state
(freeze_top_layer's snowy dirt). The spawn box check uses the common mob size (0.6 x 1.8), as the placement
rules carry no entity dimensions.

## Fallback and follow-ups

- If a game update breaks the hook, F4 can construct the generator through `ext::createGenerator`; if the
  generator subclassing breaks, the same stages can run from a `LevelChunk` load hook over a flat generator.
- U1: call `gf::worldgen::ext::setPossibleBiomes` with the biome source's list (feature seed indices depend on
  its order) and define the 22 biomes as behavior pack biomes (like the probe); keep vanilla spawn-rule tags
  off them (F5's spawner spawns their mobs from the biome JSON).
- U2: build the terrain on `core::noise::NoiseChunk` (interpolation-exact `final_density`); register carvers by
  configured carver id or type: each call is one (source chunk, index) of `applyCarvers`, already seeded;
  read the source chunk, index, configuration and the chunk's carving mask from `ext::carverContext()` and test
  `isStartChunk` (`ext::isStartChunk` for the vanilla rule, TF's highland caves always start).
- F6 / structure units: register the piece spawn indices with `gf::spawn::ext::registerSpawnIndex` (or put
  `spawn_indices` in the start's data, one per piece box); the hollow hill dome is built in. Controlled spawns
  and the no_structure placement need F6's `landmark::startsIntersecting` (a stub until F6 lands).
- F9: `gf::tags` is a stub on main; world generation already reads TF's imported block tags itself.

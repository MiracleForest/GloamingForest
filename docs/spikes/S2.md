# S2: Can the Twilight Forest generate its own chunks on Bedrock, deterministically and Java-exact, inside the custom dimension?

| | |
|---|---|
| Unit | F5 |
| Status | answered (custom biomes reach servers, clients and server maps through the chunk data) |
| Date | 2026-11-02 |
| Game / LeviLamina | 1.26.51 / 26.51.7 |

## Question

Can a mod-owned `WorldGenerator` produce every chunk of `twilightforest:twilight_forest` through a staged
pipeline (biomes, starts, noise, surface, blankets, carvers, features with structure pieces, spawns) on the
engine's generation worker threads, with the same random numbers and noise values as TF 4.8 on Java 1.21.1, and
can the chunks carry TF's custom biomes (server biomes, the client's view of them, spawn rules, map colours)?

## Why it matters

Everything world-shaped in TF depends on it: U1 (biome source, the 22 biomes), U2 (terrain, carvers, blankets),
U3 (trees), U18/U19 and every landmark unit (features, pieces, controlled spawns), U16/U17 (natural spawning),
U13 (maps), U15 (biome visuals). Parity of terrain and decoration needs bit-exact Java random sources and noises,
Java's seeding of every placed feature (`WorldgenRandom#setFeatureSeed(decorationSeed, featureIndex, step)` over
FeatureSorter's order), of every structure step and of every carver (`setLargeFeatureSeed(seed + index, sourceX,
sourceZ)`), Java's stage order and Java's biome lookups at block positions (BiomeManager's zoom).

## What was tried

1. **Java-parity core** (`src/core/jrand`, `src/core/noise`, pure C++): LegacyRandom, Xoroshiro128++
   (`RandomSupport` seeding, MD5 `fromHashOf`), WorldgenRandom (decoration, feature, large-feature, salted and
   slime seeds), positional factories, `Mth#getSeed`, String#hashCode, ImprovedNoise, SimplexNoise, PerlinNoise
   (modern and legacy), NormalNoise, PerlinSimplexNoise, the vanilla density functions with cubic splines,
   NoiseChunk interpolation, FeatureSorter, `HashSet<BlockPos>` order, `Mth#sin`, and **BiomeManager**
   (`src/core/jrand/BiomeManager.h`: `obfuscateSeed` = SHA-256 of the seed's little-endian bytes read back as
   Guava's `asLong`, `getFiddledDistance` with LinearCongruentialGenerator, the 8-corner zoom). Floating point
   code is compiled with `#pragma clang fp contract(off)`.
2. **Java oracle**: `tests/worldgen/oracle/Oracle.java` runs against the Minecraft 1.21.1 server jar (official
   mappings, reflection; JDK 21 and the jar from F13's `%LOCALAPPDATA%\gf-oracle`) and prints 107 lines (4 of them
   BiomeManager: `obfuscateSeed`, the quart `getBiome(BlockPos)` reads through a recording `NoiseBiomeSource`
   proxy, `getFiddledDistance`); `JavaParityTest` rebuilds every line and compares character for character.
3. **Generator**: `TwilightGenerator : VoidGenerator` (MCAPI constructor), installed by hooking
   `CustomDimension::$createGenerator` (MCAPI) for `twilightforest:twilight_forest`. `loadChunk` runs Biomes,
   Starts, Noise, Surface, **Blanket**, Carvers into the `LevelChunk`; `decorationPostProcessChunk` runs, for each
   `GenerationStep.Decoration` step, that step's structures (the structure steps; the plain **Pieces** stage once,
   at SurfaceStructures) then that step's placed features, then Features,
   LargeWriter and Spawns over a `BlockSource` of the 3x3 `ChunkViewSource` (Java's WorldGenRegion).
4. **Stage order as Java runs it** (`src/feature/ext/worldgen/Generation.h`):
   - Blanket at surface time: TF injects `ChunkBlanketProcessors#chunkBlanketing` right after
     `ChunkGenerator#buildSurface` in `ChunkStatusTasks#generateSurface` (tf-asm `ChunkStatusTaskTransformer`), so
     the canopy and the glacier are built over the bare ground (`WORLD_SURFACE_WG`) and every carver and feature
     sees them. `ext::blanketContext()` gives the blanket the surface step's WorldGenRegion random (each processor
     that applies forks it, as TF does) and the biomes of the chunk's sections. The contract header's stage
     comment ("Blanket" after "Pieces") is not Java's order.
   - Structures per decoration step: Java places, at each `GenerationStep.Decoration` step, the structures of that
     step before its features, each after `setFeatureSeed(decorationSeed, index, step)`, `index` counting every
     structure of the step in Java's structure registry, Minecraft's own included. The registry order is the data
     load order: `RegistryDataLoader#loadContentsFromManager` iterates a `TreeMap` from
     `MultiPackResourceManager#listResources`, and `ResourceLocation#compareTo` compares the path before the
     namespace (both checked with javap on the 1.21.1 jar), so the file paths `worldgen/structure/<path>.json` sort
     first. `ext::structuresByStep()` / `ext::structureSlot(id)` give that order (Minecraft 1.21.1's 34 structures,
     steps read from the jar's data, and TF 4.8's 21 built in, plus any structure JSON in the mod's data):
     underground_structures holds 8 (buried_treasure, knight_stronghold, labyrinth, mineshaft, mineshaft_mesa,
     trail_ruins, trial_chambers, troll_cave), surface_structures 43 (the lich tower is index 14, the yeti cave
     42), top_layer_modification the giant house alone.
   - The contract's single `Stage::Pieces` keeps its meaning: its steps run once per chunk, at SurfaceStructures
     (the step of most TF landmarks). `ext::addStructureStep` is the opt-in per-step call: it runs at every step
     with `ext::decorationContext()` (step, decoration seed, `structureRandom(index)`,
     `structureRandomOf(id)`); at SurfaceStructures both kinds run together by (order, registration).
   - Heights: `Chunk::height` is `ChunkAccess#getHeight` (the y of the highest counted block),
     `Region::height` is `WorldGenLevel#getHeight` (that y + 1).
5. **Biome lookups**: `Region::biome(pos)` is `LevelReader#getBiome(pos)`: BiomeManager's zoom over the quart
   biomes of the chunks the region holds (y clamped as `ChunkAccess#getNoiseBiome`), the biome source elsewhere
   (`getUncachedNoiseBiome`). The placement biome filter, freeze_top_layer, the chunk-generation and natural
   spawners and the blanket getter all go through it; `worldgen::biomeAt` zooms over the biome source.
   Bedrock stores and draws a biome per block, Java keeps quarts and zooms at every per-block read (its client's
   grass and water colours, precipitation, snow). The generator therefore writes the **zoomed biome of every
   block** into the game chunk (`BlockBiomeWriter`): the quarts of the chunk and of the one-quart ring the zoom
   reaches come from the biome source, a block whose 8 candidate quarts agree takes their biome without the zoom,
   each column's most frequent biome is one `_setBiome(fill)` call and the other blocks are written singly. Bedrock's
   own per-block readers then see Java's borders instead of 4 x 4 x 4 steps. The raw quarts stay available where
   Java reads them: `Chunk::biome` during loadChunk, the biome source for `noiseBiome()` of the generator's
   chunks, and each chunk's distinct raw biomes kept for the decoration's biome set.
6. **Carvers** as `ChunkGenerator#applyCarvers` (17 x 17 source chunks, `setLargeFeatureSeed(seed + k, S)`,
   `ext::carverContext()`); the chunk's carving mask is kept until its decoration, where
   `minecraft:carving_mask` (CarvingMaskPlacement) streams it in index order.
7. **Feature interpreter** (`src/feature/features`): imported configured / placed features, Java's lazy placement
   streams, 17 vanilla feature types, 20 placement modifiers (count_on_every_layer treats flowing water / lava as
   Java's water / lava; TF's `no_structure` is AvoidLandmarkModifier through F6's `landmark::ext::featureBlocked`,
   which knows the pieces' `allow_features` and owns the whole rule, Java's `StructureStart#isValid` skip of a site
   it reserved without pieces included: F5 only reads the codec fields), providers, predicates, rule tests (block tags through
   F9's `gf::tags` with the game's ids, plus the Java 1.21.1 vanilla tags its bridge lacks; the answers are kept per
   `features::detail::TagCacheScope`: a chunk's generation, its decoration, a natural spawner tick), trees with
   placers and decorators, LargeWriter.
8. **Custom biomes**: the probe `gf_test:worldgen_probe` (behavior pack biome, format 1.21.110, `minecraft:climate`
   temperature 2.0 / downfall 0.0, `minecraft:map_tints` grass and foliage `#FF00FF`) is installed into the
   deployed test pack before the world loads (`tools/e2e/server/scenarios/worldgen.probe.ps1`), plus a client look
   in the test resource pack: the current client biome format (`biomes/worldgen_probe.client_biome.json`, format
   1.21.70, as the game's own pack ships its biomes in 1.26.51: `minecraft:sky_color`, `minecraft:grass_appearance`,
   `minecraft:foliage_appearance`, `minecraft:water_appearance`, `minecraft:fog_appearance`, all magenta) and the
   legacy `biomes_client.json` for comparison. Experiments, each with a vanilla-biome control:
   - painted chunks: `worldgen.custom_biome` paints 5 x 5 chunks 3000 blocks east of the real player with the probe
     and 5 x 5 chunks 3000 blocks south with `minecraft:desert` (same painting method), and keeps both loaded with
     a ticking area until `worldgen.custom_biome_restore`; the client has never received them; the player travels
     to each and `worldgen.custom_biome_view` logs what the server and the client's own level hold under it;
   - generated chunks (f4-dimension c9a4d02 merged locally, not pushed): `worldgen.generator_view` makes the
     generator write the probe into fresh Twilight Forest chunks (20000, 20000) and sends the player there, then
     the same with `minecraft:desert` at (40000, 40000);
   - server map: `worldgen.custom_biome_map` paints one chunk column with the probe and one with the desert next to
     an unpainted (plains) one, renders a server map over them with `MapItem::sampleMapData` (MCAPI) into a
     `MapItemSavedData` from `Level::createMapSavedData` (never saved, removed from the `MapDataManager` at the end),
     locates the texels with a lapis marker and logs the grass map colour of each column;
   - remote clients (`-Mode remote-vanilla`: the game without the client mod, joined to a BDS host running the mod;
     the host has no probe): the host paints `minecraft:desert` 3000 blocks south of the player, the player goes
     there, and the screenshot's ground tint is compared with the home ground.
9. **Spawns**: tables, chunk-generation spawns (`spawnMobsForChunkGeneration` with the entity's heightmap,
   `adjustSpawnPosition` for ON_GROUND, the spawn box, the WorldGenRegion random for predicates, and the mob's
   spawn-position check before the group counts it), the natural spawner (`spawnCategoryForPosition` with the
   list re-checked at every position, the spawn box, the 24-block shared spawn exclusion, Java's global caps once
   per tick, `LocalMobCapCalculator`'s per-player caps, persistent mobs not counted, `getMaxSpawnClusterSize`,
   `isMaxGroupSizeReached`), TF's `gatherPotentialSpawns`, the structures' spawn overrides. The mob's own checks
   default to Java's base classes (javap on the 1.21.1 jar): `Mob#checkSpawnObstruction` is
   `!containsAnyLiquid(box) && isUnobstructed(this)` (WaterAnimal's: `isUnobstructed` only), and during chunk
   generation `WorldGenRegion#getEntities` is always empty, so there only the liquid check can refuse (a group's
   members may overlap); `checkSpawnRules` is the walk target value of the mob's class (`ext::WalkTarget`: Monster,

## Conclusion

Yes. The CustomDimension route gives a mod generator for the custom dimension; loadChunk and decoration
post-processing give the two halves of Java's ChunkStatus pipeline, the stages run in Java's order (blankets at
surface time, structures at their own decoration step with Java's registry-order seeds through
`ext::addStructureStep`, the contract's single Pieces stage once), the core reproduces Java's numbers bit for bit,
block-position biome lookups use Java's BiomeManager zoom, and the chunks store the zoomed biome of every block, so
Bedrock's own per-block readers see Java's borders.

Custom biomes work end to end through the chunk data:
- Server: a behavior pack biome with a namespaced id registers on BDS 1.26.51 without an experiment; the generator
  writes it; features, spawns, temperature and the biome source see it.
- Clients: the chunk's biome reaches the client's own level; vanilla clients draw a painted biome the same way
  (measured on a remote host with the probe and a vanilla biome: the probe's client biome file, sent with the host's
  resource packs, colours it there too). A resource pack **client biome file in the current format**
  (`biomes/<name>.client_biome.json`, format 1.21.70) gives a custom biome its grass and foliage colours (verified:
  magenta) and tints its clouds; its water surface took a pink tint. Fog through `minecraft:fog_appearance` and the
  legacy `biomes_client.json` did not show. TF's biome visuals therefore come from U1's biome definitions and
  U15's client biome files; F12 / U15 add what Bedrock biome files do not give (TF's sky and fog renderers through
  `client.world`'s `sky::setProvider` fog(biome) for mod clients).
- Map colours: server maps colour grass and foliage by the chunk's biome, including a custom biome's
  `minecraft:map_tints`, so U1 gives each TF biome its map tints; TF's magic / maze maps use `magic_map_color` (U13).
- Spawn rules: F5's spawner spawns the biomes' mobs from the biome JSON spawners (no vanilla spawn-rule tags on TF
  biomes, so Bedrock's own spawner adds nothing).

Limits: providers run on worker threads and touch only their chunk / region. Bedrock vines have no "up" face and
leaves no distance property; Bedrock grass has no "snowy" state. Mob size, cluster size and spawn checks default to
Java's base classes until the entity units register theirs (`spawn::ext::registerSpawnBehaviour`); generation-time
light for spawn checks is estimated from the blocks above (Bedrock lights chunks later). A biome changed with
`Chunk::setBiome` during generation does not re-zoom its neighbours (biomes come from the biome source). Chunks of
the Twilight Forest generated before this change hold raw quarts (development worlds only).

## Fallback and follow-ups

- If a game update breaks the hook, F4 can construct the generator through `ext::createGenerator`.
- U1: `gf::worldgen::ext::setPossibleBiomes` with the biome source's order; the 22 biomes as behavior pack biomes
  with climate and `minecraft:map_tints`; no vanilla spawn-rule tags.
- U2: terrain on `core::noise::NoiseChunk`; carvers through `ext::carverContext()`; blankets are called at surface
  time with `ext::blanketContext()` (fork its `regionRandom` per processor that applies, read `chunkBiomes`).
- F6 / structure units: a plain `Stage::Pieces` step runs once per chunk (at SurfaceStructures), so F6's current
  `landmark.pieces` keeps working unchanged. For Java's exact seeding and step, move it to `ext::addStructureStep`:
  per call place only the structures of `decorationContext()->step`, each with `structureRandomOf(id)`
  (`structureSlot(id)`: the index among every structure of the step, Minecraft's own included). Re-verified with F6
  on main (W0c, `worldgen.landmark_rules` over a start `landmark::forceStart` made): the controlled spawns and spawn
  overrides are F6's `structureSpecialSpawns` (`onSpecialSpawn`), `no_structure` asks F6's `ext::featureBlocked`; the
  engine's own evaluation (which read `spawn_indices` / `allow_features` from `Start::data`, which F6 never writes,
  and so gave every piece spawn index 0) and `spawn::ext::registerSpawnIndex` / `registerSpawnArea` are gone. The
  hollow hills' `HollowHillStructure#canSpawnMob` dome belongs in their `landmark::Generator::spawnIndex` (U18), or
  in F6's `potentialSpawns` for the type `twilightforest:hollow_hill`; until then a hollow hill's monsters come from
  list 0 over its whole start box. Settled with F6 in W0d (F6's #38 on main):
  - `ext::featureBlocked` and `decorationAllowed` skip a reserved site (no generator yet, no pieces), as Java's
    AvoidLandmarkModifier skips a start that is not `StructureStart#isValid`. The rule has one owner, F6: F5's own
    skip in `no_structure` is gone, and `no_structure` passes the codec fields to `featureBlocked` unchanged
    (`worldgen.landmark_rules` still checks a forced dark tower site without pieces: no feature removed, the biome's
    spawns).
  - `worldgen.landmark_rules` forces its starts with `landmark::ext::ScopedStart` (`ext/landmark/LandmarkTest.h`) in
    every world, no longer only in the e2e world `GF-Test`; the scopes remove them when the test ends (a start they
    replaced is put back), and the test checks that the start counts of the three chunks are back as it found them.
  - F6's real `structureSpecialSpawns` is tested end to end through the spawner (`spawn::detail::spawnListAt`):
    `gf_test:landmark_fixture`'s `Generator::spawnIndex` gives labelled list 1 on the shell's upper floor, list 0 on
    the porch and the biome's monsters on its ground floor; `gf_test:landmark_fixture_open`'s spawn overrides give
    the witch / creeper list in its pieces ("piece") and no ambient mobs in its box ("full"), the biome's lists
    beside them. The tests' own special spawn function stays only to show the order of the chain (registered after
    F6's: not asked where F6 answers, asked where F6 passes).
- Entity units: `spawn::ext::registerSpawnBehaviour` for size, cluster size and spawn checks (TF's ghasts, golems,
  kobolds, penguins, giant miners, ...): `walkTarget = WalkTarget::Zero` for a creature that is not an Animal,
  `obstruction = Obstruction::EntitiesOnly` for WaterAnimal-like mobs outside the water categories;
  `setPlacementHeightmap` where an entity registers another heightmap.
- F9: re-verified on main (W0c, `worldgen.tags`): `kit::hasTag` asks `tags::has` with the block's game (Bedrock) id
  and the spawner's biome tags go to it too; the data tag files fallback is gone. Built in stay only the vanilla
  1.21.1 tags the bridge does not answer (`minecraft:fences`, `doors`, `trapdoors`, `overworld_natural_logs`, the
  river biome tags) and `#minecraft:leaves` inside `minecraft:replaceable_by_trees` (the bridge's include reaches only
  the vanilla leaves, not TF's added by its data). `kit::isReplaceable` is `BlockState#canBeReplaced`: vanilla's
  replaceable blocks and TF's four (`TFBlocks`). `tags::has` builds key strings and takes a process-wide mutex per
  call, so `kit::hasTag` keeps its answers per (tag, block) inside a `TagCacheScope` (never across one: F9's data
  reloads on `/twilightforest reload` and in its selftests). Open with F9: a bridged tag's `include` resolves only
  the included tag's bridge rule, not TF's data members of it, so `twilightforest:carver_replaceables` (via
  `#minecraft:overworld_carver_replaceables` -> `#minecraft:dirt`) misses `twilightforest:uberous_soil`,
  `twilightforest:worldgen_replaceables` (via `#minecraft:lush_ground_replaceable` -> `#minecraft:moss_replaceable`)
  misses TF's root, liveroot block, trollsteinn and uberous soil, and `minecraft:lava_pool_stone_cannot_replace`
  misses TF's leaves and logs; the bridge also lacks `fences`, `doors`, `trapdoors`, `overworld_natural_logs` and the

# S3: Can custom TF blocks hold a real container (block entity) that persists and opens a container screen on every client?

| | |
|---|---|
| Unit | F10 |
| Status | answered with a fallback |
| Date | 2026-11-02 |
| Game / LeviLamina | 1.26.51 / 26.51.7 |

## Question

TF's chests, keepsake casket, drying racks, jars, the uncrafting table and the cinder furnace are block
entities with inventories. Custom Bedrock blocks have no block entities of their own. Does Bedrock
1.26.51 let a data-driven (add-on) block carry a container block actor that (a) the server can fill,
(b) survives a world reload and (c) opens as the game's own container screen on the client mod and on
a vanilla client? Is the `minecraft:container` component (or an experiment / level-data flag that
unlocks it) usable, or does gf::inventory need another backend?

## Why it matters

`gf::inventory` (feature/inventory/Inventory.h) hides the backend from U4 (chests), U9 (casket),
U13 (uncrafting table), U22 (jars, candles) and the others; `gf::loot::placeContainer` fills TF's
structure chests through it. A real game container gives every client the game's container screen,
the game's item transactions and persistence with the block; anything else needs our own storage and
our own screens.

## What was tried

1. **The block component names.** `BlockContainerDescription::NameID()` / `BlockBlockEntityDescription::NameID()`
   are `minecraft:container` and `minecraft:block_entity` (both exist in 1.26.51, together with
   `DataDrivenBlockActor`, `ContainerBlockActorComponent`, `DataDrivenBlockContainer` and
   `ContainerType::DataDrivenContainer = 37`). Probe blocks `gf_s3:*` in a throw-away behavior pack
   written by `tools/e2e/server/scenarios/combat.s3.prelaunch.ps1`, checked by the selftests
   `combat.s3_probe`, `combat.s3_persist_write`, `combat.s3_persist_read`
   (`src/feature/inventory/S3Probe.cpp`).
2. **`minecraft:container` in a block definition.**
   - format_version 1.21.40: `child 'minecraft:container' not valid here` (and the same for
     `minecraft:block_entity`).
   - format_version 1.26.50: `minecraft:container: this component was found in the input, but is not
     present in the Schema`; `minecraft:block_entity` is accepted.
3. **Experiments / level-data flag.** The probe module can force `AllExperiments` flags into the level
   data when level.dat is read (`Experiments::getTagData` hook, `$env:GF_S3_EXPERIMENTS`). With every
   toggle forced (1, 3, 5-7, 9-23) the server reports `Experiment(s) active: gtst, vtra, epoi, cwcl` and
   `minecraft:container` is still not in the schema.
4. **The component registry.** `BlockComponentFactory::registerAllCerealDescriptions` hooked: the cereal
   component map has `minecraft:geometry` (released 1.19.40) but no `minecraft:container` (nor
   `minecraft:block_entity`, which comes from the legacy descriptions): there is nothing to unlock by
   clearing load requirements.
5. **`minecraft:block_entity` alone** (format_version 1.26.50, with geometry): the block gets a
   `DataDrivenBlockActor` (BlockActorType 62) with no container component.
6. **Injected container.** `ContainerBlockActorComponent::tryCreateFor(BlockType const&)` (MCAPI, static)
   hooked: for a block registered with gf::inventory it returns our component with the same layout
   (vtable + `unique_ptr<Container>`): a `Container` subclass (`Container(ContainerType::Container)`
   is MCAPI) with N slots, saved / loaded by the component's `save` / `load` into the block actor's own
   NBT ("GfItems", GloamingForest item JSON). Registrations happen at mod load (data-declared
   containers), before any chunk of a world loads.
7. **The screens.** `ServerPlayer::openUnmanagedContainer(ContainerType, BlockPos)` (MCAPI) asked to
   open the game's screen for the injected container, as `ContainerType::Container` (0) and as
   `ContainerType::DataDrivenContainer` (37), for the local player (`combat.ui_native_container`,
   `gf::inventory::openNativeScreen`). Blocks without `minecraft:block_entity` keep their slots in
   BlockData. Both backends are shown in the client mod's chest screen (`inventory.chest`,
   `src/client/inventory/ChestScreen.cpp`) or a form on vanilla clients.
8. **Loot in vanilla containers.** Chests placed by `gf::loot::placeContainer` keep the Java table in
   the native loot field (`gf_loot:<table>#<seed>`). The game's chest screen does not pass through
   `RandomizableBlockActorContainerBase::unPackLootTable` (hooked, but not hit by an opening), so a
   high-priority `interactions` use-on / destroy handler of the randomizable vanilla container
   blocks (chests, barrels, shulker boxes, dispensers, droppers; not a sneaking use-on with an item,
   which places) rolls the table (LootTable#fill) before vanilla opens or breaks the container. The
   hook stays for the other unpack paths.
9. **The game's container screen on a vanilla client (container-entity route).** A client opens a
   container screen only for a container it knows itself: a vanilla block actor or an entity with a
   container. A custom block has neither on the client (its data-driven block actor carries no
   container there, step 7), and a remote vanilla client has no behavior pack definitions, so a
   custom entity with `minecraft:inventory` is not known either. The proxy is a vanilla
   `minecraft:chest_minecart` (27 slots, known to every client)
   (`src/feature/inventory/VanillaContainer.cpp`):
   - spawned inside the container block (`CommandUtils::spawnEntityAt`), invisible, without gravity,
     collision, AI or hitbox (a zero bounding box, so other players still reach the block), tagged
     `gf_inventory_proxy`, titled with the container's title (the entity's name tag: the screen
     shows it, `ContainerComponent::setCustomName` alone left "Minecart with Chest"; the name is not
     drawn above the hidden proxy);
   - opened with `Actor::openContainerComponent` 3 ticks after the spawn (the client must have the
     entity first);
   - one copy of the slots while open (review round 2 found a duplication with a 5-tick storage
     read): the storage stays the only copy and the proxy mirrors it. A content change listener on
     the proxy's container writes every change of the screen (the game's item transactions,
     shift-clicks, drag-splitting) to the storage as it happens; every write through a handler from
     `gf::inventory::find` (the client mod's screen, forms, units) and the injected container's own
     `setItem` (game code that sets its slots) reaches the proxy at once. Writes behind the handler
     (a unit's own get / set storage changed directly) are pulled in right before each item request
     of a viewer's client (one `ServerNetworkHandler::handle(ItemStackRequestPacket)` hook: the
     request then works on the storage's slots, a stale stack fails the request's own check and the
     client is resynced) and every tick; a slot changed on both sides keeps the storage's stack, and
     the listener itself checks the storage's slot against the last agreed one before it writes
     (review round 3: the same slot written behind the handler and taken in the screen in one tick
     keeps the storage's stack). A Handler with its own get / set should still write through
     `find`'s handler while a screen may be open. A block change at the position ends the session at
     once without touching the storage (the storage's copy drops, the proxy is emptied and removed),
     before any later click can reach it. On close (the player's `ContainerManagerModel` is no longer
     the proxy's) or when the player leaves: the proxy is emptied and removed; a player who closed
     the screen and uses the block again before the next tick opens it again in the same session;
   - protected: damage is cancelled (`gf::combat::onIncoming`, highest priority), attack is denied and
     interact opens the container it stands for (`gf::interactions`); a proxy that outlived its
     session (a crash after an autosave) is removed empty by a sweep every 100 ticks (the storage has
     every change).
   Used for every 27-slot container a vanilla client opens (`openChestLike`); other sizes keep the
   form, which now also puts stacks in ("Put in": a second form lists the player's stacks). The
   fake-chest route alone (a client-only chest block over the custom block plus
   `openUnmanagedContainer`) was not taken: it needs a server block actor (the BlockData backend has
   none) and shows a vanilla chest in place of the TF block while the screen is open.
   **Double chests (W0c)**: the two routes together give a vanilla client the game's large chest
   screen of a TF double chest. The server side is the chest minecart proxy, its container made 54
   slots (`FillingContainer::clearInventory(54)`: the right half's 27 slots, then the left half's);
   the client side is a vanilla chest pair of that player's own client only (`UpdateBlockPacket` and
   `BlockActorDataPacket` with `pairx` / `pairz` / `pairlead`), 2 (else 3, 4) blocks under the
   halves in the ground and never where the server has a block actor, so nothing changes in the
   world and the TF chest stays in view (F11's lids keep moving). The minecart's
   `ContainerOpenPacket` goes out as one of type Container at the pair's lead chest
   (`ServerPlayer::sendNetworkPacket` hook, only around that open), so the client shows its large
   chest screen while the server keeps the minecart's container behind it; a client's
   `ContainerClosePacket` for it names the minecart's type again. When the screen closes (or the
   session ends) the client gets the real blocks back.
10. **JSON-UI title skin.** F12's spike S5 (`gf::ui::containerTitleSkin`, PR #17) found that the
   vanilla chest screen's JSON-UI cannot test or cut `$container_title`, so no skin is drawn and
   titles stay plain. `openChestLike` passes a declared container's `skin` through
   `containerTitleSkin` for the vanilla screen title, so a skin applies as soon as F12 lists one.

## Conclusion

- **No**: an add-on block cannot declare `minecraft:container` in 1.26.51, with or without experiments
  or a level-data flag; the component is internal (vanilla data-driven blocks).
- **Storage yes, screen no**: `minecraft:block_entity` (format_version 1.26.x) gives custom blocks a
  data-driven block actor, and one `ContainerBlockActorComponent::tryCreateFor` hook gives it a real
  game container. The container persists with the block actor and keeps the game's item handling,
  but the client does not open the game's screen for it (`openUnmanagedContainer` returns a container
  id, nothing appears).
- **The game's screen through a vanilla container entity: yes** (27 slots): an invisible, inert chest
  minecart proxy mirroring the storage (one copy of the slots) opens the game's chest screen on
  vanilla clients and on the client mod alike (local, remote-mod, remote-vanilla), with the game's
  own item transactions.
- Chosen design (`src/feature/inventory/Inventory.cpp`):
  - native backend (storage): blocks with `minecraft:block_entity` registered with gf::inventory (code
    or `assets/data/containers/<u>.json`) keep their slots in the injected container, saved with the
    block actor;
  - BlockData backend (storage): every other registered block;
  - screen for both: the client mod's chest screen (`inventory.chest`, Java's generic_54 layout and
    every ChestMenu click type: pickup, quick move, swap with the hotbar / off-hand keys, clone,
    throw, quick craft (drag-splitting), pickup all (double click), a click outside dropping the
    cursor stack; the server keeps the container it opened for each player and refuses screen data
    and actions for any other position, rows or title); on vanilla clients the game's chest screen
    through the chest minecart proxy (27 slots, step 9), the game's large chest screen for a double
    chest (the 54-slot proxy behind a client-side chest pair, step 9) or a form (take a stack, put
    stacks in) for other sizes;
  - declared chests follow ChestBlock: not opened while a redstone conductor or a sitting cat is
    above, the open / close sounds at the first opener and after the last one (the openers of every
    route are counted; `feature/ext/combat/InventoryViewers.h` gives the count to trapped chests and
    lids), the open-chest stat, and halves with a left / right chest type pair into one 54-slot
    screen (the right half first);
  - vanilla containers keep the game's own screen; TF's loot reaches them through `placeContainer`;
  - loot in custom containers: `Handler::setLootTable`, rolled on first access (Java's
    RandomizableContainer);
  - drops: a removed native container drops its slots from one `DataDrivenBlockActor::onRemoved` hook
    (emptied first, so the game cannot drop them again); a declared BlockData container drops from the
    block data erase listener (any removal: player, explosion, piston, /setblock);
  - saving: the injected container calls `BlockSource::fireBlockEntityChanged` on every change.
- Limits: the native backend needs the block JSON to declare `minecraft:block_entity`, which only
  the block formats from 1.26.20 take (spike S7: 1.26.50, with the block's tags as the
  `minecraft:tags` array; block owners: U9 casket, U22 jars, ...); a block actor made before its
  block is registered gets an empty container (registrations are at mod load to avoid that); a
  vanilla client gets the game's chest screen for 27-slot containers (the chest minecart's size)
  and double chests (54) and a form for the others; the vanilla screen's title has no TF skin (S5).
- Hoppers (W0d update): the injected container has no `IVanillaMainBlockActorComponent`, so the
  game's own lookups do not find it; F11's hooks (`src/feature/families/Hoppers.cpp`, F11's PR #32:
  `Hopper::_getContainerInBlock`, `Hopper::_getContainersAt`, `DropperBlockActor::getContainerAt`)
  show it to hoppers, hopper minecarts, droppers and crafters, a paired half as Java's 54-slot
  CompoundContainer. Which blocks: `src/feature/ext/families/Hoppers.h` (by default the chest-like
  declarations, `Declared::chest`; a unit opts other Container blocks in). TF's chests use the native
  backend: `tools/families` writes the chest families in format 1.26.50 with `minecraft:block_entity`
  (spike S7), and a chest whose stacks were stored in block data before keeps them readable until they
  move (`src/feature/ext/combat/InventoryMigrate.h`). A BlockData container stays out of a hopper's
  reach (it has no game container). A hopper that reaches the proxy minecart while a vanilla screen
  is open changes the proxy's container, and the listener writes that to the storage like a screen
  change, so no copy is made. Every write a hopper makes goes through the native container's
  `setItem`, which tells the open screens (the proxy at once, the client mod's chest screen at the
  end of the tick: `src/feature/ext/combat/InventoryChanges.h`).
- Comparators: a declared container (`comparator`, on by default) registers Java's
  `getAnalogOutputSignal` with the redstone contract (`redstone::registerAnalog`, F0's
  `ComparatorCapacitor` hook feeds it to vanilla comparators): `AbstractContainerMenu#getRedstoneSignalFromContainer`
  over its slots (`Mth.lerpDiscrete(sum(count / min(99, max stack)) / slots, 0, 15)`), a double
  chest's two halves together, 0 while a chest is blocked (`ChestBlock#getContainer` finds none),
  and reading the slots rolls a pending loot table first (Java's `RandomizableContainer#getItem`).
  Code-registered containers (`registerBlock`) add their own through `redstone::registerAnalog`.

## Fallback and follow-ups

- If `tryCreateFor` changes in a game update, gf::inventory keeps working on the BlockData backend for
  every block (same screens).
- Vanilla clients: the chest minecart proxy covers 27 slots; a hopper minecart (5 slots) could
  cover TF's 5-slot containers the same way if a unit needs it. `gf::inventory::openNativeScreen`
  keeps the injected-container experiment reachable for the next game version.
- Follow-ups: F11 adds `minecraft:block_entity` to the generated JSON of container families (done
  for the chests in F11's PR #32, with the hopper hooks above); U9 / U22 declare their containers in
  `assets/data/containers/<u>.json`; F12's `ContainerScreen` can replace the plain chest screen with
  TF's GUI textures.

## Audit round 1

Checked: the recursion guard of the damage pipeline, handler registration and removal of the
combat and loot contracts.

Fixed:
- A hurt started inside an `onIncoming` / `onDealt` handler skipped every handler when its victim's
  handlers were running (only damage to other victims ran them). The guard is per attack now:
  the same attack (victim, damage type, attacker, direct entity) on top of itself passes through
  as is, anything else runs the handlers again (Java's nested damage events:
  EntityUtil#properlyApplyCustomDamageSource, a part forwarding to its parent), at most 8 deep
  per victim. Selftest `combat.nested_hurt`.
- `gf::combat::ext::addIncoming` / `addDealt` / `remove` and `gf::loot::ext::addEntityDrops` /
  `removeEntityDrops` (feature/ext/combat/Handles.h): the same registrations with a handle.

- `DamageInfo::attacker` / `direct` of a projectile's damage were the wrong way round: Bedrock's
  ActorDamageByChildActorSource(child, owner) answers getEntityUniqueID with the owner and
  getDamagingEntityUniqueID with the child (measured by `combat.child_source`), and the pipeline
  read them the other way. Now attacker = the owner (DamageSource#getEntity), direct = the
  projectile (#getDirectEntity), for gf::combat::hurt and the game's own projectiles alike.

Open:
- Units that worked around the swapped pair can drop it: U24 hydra and U8 weapons
  (`World.cpp causingAndDirect`, now a no-op for correct pairs), U26 darktower
  (`UrGhast.cpp reflectedFireball` and the fireball / player pick at ~1291 and ~1342 accept both
  orders), U21 lich (`Projectiles.cpp` ~336-353 accept both). U9 `WandBolt.cpp:119` and U7
  `armory/Module.cpp:173` read the pair as documented and are right only now.
- U29 giants (`Mobs.cpp`, GiantMiner's ant damage) defers its re-dealt hurt to the next tick only
  because nested hurts skipped the handlers; it can deal it inside the handler now.

## Audit round 2

Checked: the damage pipeline against handlers that change the damage type and handlers that deal
the hit again (EntityUtil#properlyApplyCustomDamageSource, Wraith#doHurtTarget, FireBeetle's
breath), the loot contract's containers against TF's camp pots, the native container backend
against WorldlyContainer sides.

Fixed:
- A handler may change `DamageInfo::type`: the handlers after it see the new type, the hit lands as
  that type (its Bedrock cause, knockback rule, death message, exhaustion; onDealt hears the new
  type; a player's exhaustion is the new type's only) and the incoming handlers that already ran on
  it do not run again, so their modifiers apply once. Units no longer need to cancel and deal the hit again a tick later (U17's haunt / clamped /
  scorched, reported in docs/units/hostiles.md).
- Re-entrant conversions: a gf::combat::hurt of the same victim by the same attacker and direct
  entity, with the amount the hit's handlers left, started from an onIncoming handler (cancel + deal
  it again as another type) continues the hit (an extra hit of another amount is a hit of its own): the handlers before the converter are skipped (their changes are in the amount handed on),
  the converter and the ones after it run with the new type. Another victim, attacker or direct
  entity still runs every handler (part forwarding, reflections). Selftest `combat.type_change`
  (both forms: the modifier before the converter applies once, onDealt hears the new type once);
  `combat.nested_hurt` unchanged.
- Decorated pots take loot tables (DecoratedPotBlockEntity is a RandomizableContainer): the loot
  contract's vanilla containers include `minecraft:decorated_pot`, the table is rolled into its one
  slot when it is first used or broken. The structure kit's `camp_pot` marker (U19's camps) now
  fills its pots. Selftest `combat.loot_decorated_pot`.
- WorldlyContainer sides: `gf::inventory::ext::setFaceRules(blockId, {slotsForFace,
  canPlaceThroughFace, canTakeThroughFace})` (feature/ext/combat/InventoryFaces.h); the native
  backend's game container answers the game's hoppers, hopper minecarts and droppers by them
  (Container::canPushInItem / canPullOutItem with the side), F11's double chest view included.
  Selftest `combat.inventory_faces` (the rule, and a vanilla hopper on a chest with an UP rule).

Open:
- U30 to give the cinder furnace its sides (UP [0], DOWN [2, 1] with only a bucket out of 1, sides
  [1]) with setFaceRules.
- The side rules need the native container's position, which F11's hopper lookup
  (inventory::nativeContainer) sets before the game's hopper reaches the container; game code that
  finds the block actor without it gets the plain Container answer.
- A hopper pulling from a decorated pot that still holds its table: Bedrock's pot may hand out its
  item without unPackLootTable (the use and break paths unpack first).

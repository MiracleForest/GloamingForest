# S3: Can custom TF blocks hold a real container (block entity) that persists and opens a container screen on every client?

| | |
|---|---|
| Unit | F10 |
| Status | answered with a fallback |
| Date | 2026-11-02 |
| Game / LeviLamina | 1.26.51 / 26.51.7 |

## Question

TF's chests, keepsake casket, drying racks, jars, the uncrafting table and the cinder furnace are block
entities with inventories. Custom Bedrock blocks have no block entities of their own. Does Bedrock
1.26.51 let a data-driven (add-on) block carry a container block actor that (a) the server can fill,
(b) survives a world reload and (c) opens as the game's own container screen on the client mod and on
a vanilla client? Is the `minecraft:container` component (or an experiment / level-data flag that
unlocks it) usable, or does gf::inventory need another backend?

## Why it matters

`gf::inventory` (feature/inventory/Inventory.h) hides the backend from U4 (chests), U9 (casket),
U13 (uncrafting table), U22 (jars, candles) and the others; `gf::loot::placeContainer` fills TF's
structure chests through it. A real game container gives every client the game's container screen,
the game's item transactions and persistence with the block; anything else needs our own storage and
our own screens.

## What was tried

1. **The block component names.** `BlockContainerDescription::NameID()` / `BlockBlockEntityDescription::NameID()`
   are `minecraft:container` and `minecraft:block_entity` (both exist in 1.26.51, together with
   `DataDrivenBlockActor`, `ContainerBlockActorComponent`, `DataDrivenBlockContainer` and
   `ContainerType::DataDrivenContainer = 37`). Probe blocks `gf_s3:*` in a throw-away behavior pack
   written by `tools/e2e/server/scenarios/combat.s3.prelaunch.ps1`, checked by the selftests
   `combat.s3_probe`, `combat.s3_persist_write`, `combat.s3_persist_read`
   (`src/feature/inventory/S3Probe.cpp`).
2. **`minecraft:container` in a block definition.**
   - format_version 1.21.40: `child 'minecraft:container' not valid here` (and the same for
     `minecraft:block_entity`).
   - format_version 1.26.50: `minecraft:container: this component was found in the input, but is not
     present in the Schema`; `minecraft:block_entity` is accepted.
3. **Experiments / level-data flag.** The probe module can force `AllExperiments` flags into the level
   data when level.dat is read (`Experiments::getTagData` hook, `$env:GF_S3_EXPERIMENTS`). With every
   toggle forced (1, 3, 5-7, 9-23) the server reports `Experiment(s) active: gtst, vtra, epoi, cwcl` and
   `minecraft:container` is still not in the schema.
4. **The component registry.** `BlockComponentFactory::registerAllCerealDescriptions` hooked: the cereal
   component map has `minecraft:geometry` (released 1.19.40) but no `minecraft:container` (nor
   `minecraft:block_entity`, which comes from the legacy descriptions): there is nothing to unlock by
   clearing load requirements.
5. **`minecraft:block_entity` alone** (format_version 1.26.50, with geometry): the block gets a
   `DataDrivenBlockActor` (BlockActorType 62) with no container component.
6. **Injected container.** `ContainerBlockActorComponent::tryCreateFor(BlockType const&)` (MCAPI, static)
   hooked: for a block registered with gf::inventory it returns our component with the same layout
   (vtable + `unique_ptr<Container>`): a `Container` subclass (`Container(ContainerType::Container)`
   is MCAPI) with N slots, saved / loaded by the component's `save` / `load` into the block actor's own
   NBT ("GfItems", GloamingForest item JSON). Registrations happen at mod load (data-declared
   containers), before any chunk of a world loads.
7. **The screens.** `ServerPlayer::openUnmanagedContainer(ContainerType, BlockPos)` (MCAPI) asked to
   open the game's screen for the injected container, as `ContainerType::Container` (0) and as
   `ContainerType::DataDrivenContainer` (37), for the local player (`combat.ui_native_container`,
   `gf::inventory::openNativeScreen`). Blocks without `minecraft:block_entity` keep their slots in
   BlockData. Both backends are shown in the client mod's chest screen (`inventory.chest`,
   `src/client/inventory/ChestScreen.cpp`) or a form on vanilla clients.
8. **Loot in vanilla containers.** Chests placed by `gf::loot::placeContainer` keep the Java table in
   the native loot field (`gf_loot:<table>#<seed>`). The game's chest screen does not pass through
   `RandomizableBlockActorContainerBase::unPackLootTable` (hooked, but not hit by an opening), so a
   high-priority `interactions` use-on / destroy handler rolls the table (LootTable#fill) before
   vanilla opens or breaks the container. The hook stays for the other unpack paths.

## Conclusion

- **No**: an add-on block cannot declare `minecraft:container` in 1.26.51, with or without experiments
  or a level-data flag; the component is internal (vanilla data-driven blocks).
- **Storage yes, screen no**: `minecraft:block_entity` (format_version 1.26.x) gives custom blocks a
  data-driven block actor, and one `ContainerBlockActorComponent::tryCreateFor` hook gives it a real
  game container. The container persists with the block actor and keeps the game's item handling,
  but the client does not open the game's screen for it (`openUnmanagedContainer` returns a container
  id, nothing appears).
- Chosen design (`src/feature/inventory/Inventory.cpp`):
  - native backend (storage): blocks with `minecraft:block_entity` registered with gf::inventory (code
    or `assets/data/containers/<u>.json`) keep their slots in the injected container, saved with the
    block actor;
  - BlockData backend (storage): every other registered block;
  - screen for both: the client mod's chest screen (`inventory.chest`, TF's ChestMenu clicks: pick,
    place, split, swap, quick move); a form for vanilla clients (take a stack per button);
  - vanilla containers keep the game's own screen; TF's loot reaches them through `placeContainer`;
  - loot in custom containers: `Handler::setLootTable`, rolled on first access (Java's
    RandomizableContainer);
  - drops: a removed native container drops its slots from one `DataDrivenBlockActor::onRemoved` hook
    (emptied first, so the game cannot drop them again); a declared BlockData container drops from the
    block data erase listener (any removal: player, explosion, piston, /setblock);
  - saving: the injected container calls `BlockSource::fireBlockEntityChanged` on every change.
- Limits: the native backend needs the block JSON to declare `minecraft:block_entity` (block owners:
  U4 chests, U9 casket, U22 jars, ...; F11's families kit should add it to the `chest` family); a block
  actor made before its block is registered gets an empty container (registrations are at mod load to
  avoid that); hoppers and comparators do not see the injected container (no
  `IVanillaMainBlockActorComponent`); vanilla clients get a form, not a container screen, for TF's
  custom containers.

## Fallback and follow-ups

- If `tryCreateFor` changes in a game update, gf::inventory keeps working on the BlockData backend for
  every block (same screens).
- A vanilla-client container screen for custom blocks still needs a route: a fake client-side chest
  plus a server ContainerManagerModel bound to our container, or an entity container (an entity with
  `minecraft:inventory`, owned by F8). `gf::inventory::openNativeScreen` keeps the experiment
  reachable for the next game version.
- Follow-ups: F11 adds `minecraft:block_entity` to the generated JSON of container families; U4 / U9 /
  U22 declare their containers in `assets/data/containers/<u>.json`; F12's `ContainerScreen` can
  replace the plain chest screen with TF's GUI textures.

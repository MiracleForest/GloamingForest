# S6: Can TF's enchantments, effects, banner patterns, trim materials, music discs and creative tabs exist on Bedrock without breaking vanilla clients?

| | |
|---|---|
| Unit | F9 |
| Status | answered with a fallback (enchantments, effects, catalog: yes; banner patterns: safe, but drawn wrong on vanilla clients; trim materials and record sounds: feasible from the headers, to be proven by U7 / U10 with the first real item) |
| Date | 2026-11-02 |
| Game / LeviLamina | 1.26.51 / 26.51.7 |

## Question

Bedrock's registries that TF extends are closed enums or hard-coded lists that vanilla clients also
hold: `Enchant::Type` (42 enchantments), `MobEffectIds` (38 effects), `BannerPattern::mPatterns()`,
`TrimMaterialRegistryHardCodedInit::getMaterials()`, the record component's sound event, the creative
catalog's groups. For each: can TF's entry exist (server and client mod), and does a vanilla client
that receives it keep working and show something sensible?

## Why it matters

- TF's four enchantments (fire_react, chill_aura, destruction, renewal; U10) and the frosted effect
  (U10, used by the ice bow, ice sword, chill aura, snow queen, ...) are referenced across W1.
- Nine boss banner patterns (U5), six trim materials (U7), nine music discs (U10) and four creative tabs
  (F9 / F1) are TF content that vanilla clients will meet on a BDS.
- Item tooltips, glint, rarity colours and bars are part of "every screen matches".

## What was tried

1. **Enchantments**: the levels live in the stack's user data (`gf:enchant` {id: level}), are written as
   gray lore lines named like enchantments ("Fire React II", Java's `Enchantment#getFullname`), and an
   empty vanilla enchantment list (`ench: []`) marks the stack enchanted for the glint
   (`src/feature/enchant/Enchant.cpp`, `updateGlint`). The engine paths are hooked where Bedrock
   computes them: `EnchantUtils::combineEnchantedItems` (anvil: Java's AnvilMenu merge, exclusive sets,
   supported items, anvil cost), `EnchantUtils::removeEnchants` and
   `CraftHandlerGrindstone::_getExperienceFromItem` (grindstone), `EnchantingContainerManagerModel::
   recalculateOptions` + `CraftHandlerEnchant::$_handleCraftAction` + `ItemStackBase::
   saveEnchantsToUserData` (enchanting table, Java's `selectEnchantment` seeded like the table; adapted
   from Levitate). All MCAPI.
2. **Effects**: a custom effect is native state with a vanilla carrier (`src/feature/effects/Effects.cpp`):
   frosted = Slowness of the same amplifier with `mEffectVisible = false`; persisted as an actor tag
   (`gf_fx|<id>|<amplifier>|<ticks>`), Java's `MobEffectInstance#update` rules, the carrier's loss
   (milk) ends it; companions get `effects.sync` for the HUD icon.
3. **Banner patterns**: read `BannerPattern::mPatterns()`; a banner item whose `Patterns` list holds an
   id no client knows (`gf_test_pattern`) is saved / loaded on the server and given to a vanilla client
   (`item.spike_banner_registry`, `item.spike_client`).
4. **Trim materials**: read `TrimMaterialRegistryHardCodedInit::getMaterials()` (`item.spike_trim_materials`).
5. **Record sounds**: header analysis of `RecordItemComponent` (1.26.51): `mSoundEvent` is a
   `SoundEventIdentifier` = `std::variant<std::monostate, LevelSoundEvent, std::string>`; the beta
   component data (`SharedTypes::Beta::RecordItemComponent`) carries a `SoundEventName` string.
6. **Catalog**: read the server's `CreativeItemRegistry` (groups, entries) through
   `level.getItemRegistry().getCreativeItemRegistry()`; write data into its entries (the creative
   default enchantments of `showEnchantmentsOnItems`, units' default data) at world ready.
7. **Attachables**: not exercised (no armour item exists before F1 / F2 / U7); they are resource pack
   files (F2's `tools/models/attachable.ps1`), a vanilla mechanism.

## Evidence

Selftests (`tools/e2e/server/scenarios/item.ps1`, BDS, exit 0: `SELFTEST DONE pass=20 fail=0` for
`item.*`, `pass=5 fail=0` for `item.spike_*`):

- `item.spike_banner_registry`: `banner patterns: 44` (a fixed vector), `cre` known, `gf_test_pattern`
  not; the unknown id survives the server's save / load:
  `{Base:15, Patterns:[{Color:1, Pattern:"cre"}, {Color:4, Pattern:"gf_test_pattern"}], Type:0}`.
- `item.spike_trim_materials`: `quartz iron netherite redstone copper gold emerald diamond lapis amethyst
  resin` (11 materials, a hard-coded list).
- `item.spike_catalog_groups`: `creative groups: 124, e.g. itemGroup.name.planks itemGroup.name.walls ...`.
- `item.spike_glint_marker` / `item.enchant_anvil`: a custom enchantment alone makes
  `ItemStackBase::isEnchanted()` true with no vanilla enchantment in the list; the anvil merges equal
  levels to the next one, keeps the higher level, refuses an exclusive one; the grindstone removes the
  custom enchantments and pays their min cost as experience.
- `item.effect_carrier`: Slowness II on the player with hidden particles, the tag written, the state
  read back from the tag after the memory is dropped, the effect gone one tick after the carrier is
  removed, `effects.sync` sent to a companion.

Client (BeDD, `tools/e2e/client/scenarios/item.ps1`, exit 0 in `-Mode local` and
`-Mode remote-vanilla`; screenshots `tools/e2e/client/out/item-*/`):

- remote-vanilla `tooltip-fixture.png`: the hover text of the fixture item reads
  "**Fixture Item**" (aqua, the enchanted rarity as Java's), "S6 tooltip line", "Fixture React II" in
  gray; the icon has the glint.
- remote-vanilla `tooltip-sword.png`: "**Iron Sword**" (aqua), "+6 Attack Damage", "Fixture React III";
  the sword in hand and in the slot carries the glint although its only enchantment is custom.
- remote-vanilla `tooltip-banner.png` / `slot3-banner.png`: the client stays connected; the unknown
  pattern is drawn as the `base` pattern (a full field in the pattern's colour) and its hover line is the
  untranslated `item.banner.base.blue`.
- remote-vanilla `hud-carriers.png`: the carrier's effect icon is on the HUD (top right).
- The client never disconnected and the host answered selftests afterwards (`item.tags_fixture`).

## Conclusion

- **Enchantments: yes.** User data + lore + the empty vanilla list give vanilla clients Java's look
  (gray enchantment lines, aqua name, glint). The anvil, grindstone and table paths are hooked on the
  server; the anvil's preview on a vanilla client does not show the custom merge (the client computes
  its own preview), the taken result does. TF 4.8 puts none of its enchantments into
  `#minecraft:in_enchanting_table` (or `tradeable` / `on_random_loot`), so the table never offers them,
  as on Java; they come from loot (F10's loot functions call `gf::enchant::set`).
- **Effects: yes**, through carriers. Vanilla clients see the carrier's icon and predict its movement
  effect (Slowness for frosted = TF's attribute modifier); the client mod gets the exact effect list
  (`effects.sync`) for TF's icon (drawn through F12's HUD layers once they land).
- **Banner patterns: safe, but not drawn.** A vanilla client survives unknown pattern ids but draws
  them as a full `base` field with an untranslated line, so the server must not send TF's pattern ids
  to vanilla clients: U5 strips (or maps) TF patterns from banner data sent to non-companions; the
  client mod can add them to its own `BannerPattern::mPatterns()` (append a `BannerPattern`; its
  constructors are MCAPI) with the RP textures.
- **Trim materials: feasible.** The list is the return value of an MCAPI function
  (`TrimMaterialRegistryHardCodedInit::getMaterials`), so U7 can append TF's six (material id, colour
  code, item) on server and client; vanilla clients get them through `TrimDataPacket` and need the RP's
  palette textures. To be proven by U7 with its first trimmed armour (screenshot on a vanilla client);
  fallback: strip unknown materials from item data sent to vanilla clients.
- **Record sounds: feasible.** 1.26.51's record component takes a sound event *name* (variant
  alternative `std::string`, beta component `SoundEventName`), so TF's discs can name
  `twilightforest:music_disc.*` events in their BP item JSON. To be proven by U10 with the first disc;
  fallback (as the plan's deviation says): a jukebox hook plays the disc with `PlaySoundPacket` and
  keeps the comparator output.
- **Creative tabs: yes, as catalog groups.** The BP `item_catalog` declares the four groups (F1's
  import of TFCreativeTabs), the server's registry holds them, `gf::catalog` reads them back in order;
  item data of catalog entries (the default enchantments, units' defaults through
  `ext/item/Catalog.h`) is written into the registry. Bedrock's server cannot add entries at runtime
  (`CreativeItemRegistry::newItemEntry` exists only on the client), so variants of one item (TF's three
  caskets, the glass sword's lore version) need their own catalog entries in the data.
- **Attachables**: not exercised here (no armour item yet); a resource pack mechanism owned by F2 / U7.
- Tooltips, rarity and bars: tooltips are server lore in the holder's language for every client; the
  TWILIGHT rarity's dark green name and `setBar` bars are drawn by the client mod (hooks on
  `ItemStackBase::_getHoverFormattingPrefix`, `InventoryItemRenderer::$render`); vanilla clients see
  Bedrock's own name colour and durability bar.

## Fallback and follow-ups

- If the empty `ench` list stops giving the glint after an update, a placeholder vanilla enchantment is
  no way out (the client would list it); the fallback is the `minecraft:glint` item component on items
  that are always enchanted, and lore without glint otherwise.
- U5: strip TF banner patterns for vanilla clients (the `item.spike_client` banner shows why); register
  them client-side for the client mod.
- U7: append the trim materials in a hook of `getMaterials`; verify a vanilla client with a screenshot.
- U10: the discs' `minecraft:record` with a custom `sound_event`; the frosted effect registers with
  `.carrier = "minecraft:slowness"` and TF's colour 0x56CBFD.
- F12: the HUD layer `item.effects` (client/item) draws custom effect boxes once `hud::addLayer` is
  implemented; the tooltip of the client mod is the server's lore (no separate client tooltip).
- Deviation recorded: the anvil preview of a vanilla client shows the vanilla part only.

# S5: Can one F12 client contract drive TF's screens, HUD, world rendering and atmosphere on Bedrock, under Classic and Vibrant Visuals, with vanilla fallbacks?

| | |
|---|---|
| Unit | F12 |
| Status | answered with a fallback (vanilla container skins: no) |
| Date | 2026-11-02 |
| Game / LeviLamina | 1.26.51 / 26.51.7 |

## Question

Do the RenderDragon / UI entry points the F12 contracts need (UI render events, the level renderer's
block-entity pass, item frames, head gear and maps, the sky / fog / weather functions, the tint
resolver, key mappings, the local player's tick, the server's auth input) work in the shipping client
under both graphics modes, so that W1 units can draw TF's GUIs, HUD overlays, toasts, world-space lines
and geometry, item renderers in every context, map icons, skies and fog without hooking the engine
themselves (rule R8)? And do vanilla clients get usable fallbacks (forms, DDUI, JSON-UI container
skins) without companion packets?

## Why it matters

Every TF screen (UncraftingScreen), overlay (ItemDisplayOverlay, ShieldOverlay, QuestingRamIndicator,
PortalOverlay), toast (LockedBiomeToast, MissingAdvancementToast), block / item / entity renderer
(trophies in frames and on heads, casket, red thread, protection boxes), the Twilight sky / fog / aurora /
locked-biome weather (U15), the 29 TF particles, the magic / maze map icons (U13), TF's 4 keybinds
(U11/U12) and the client-authoritative movement modifiers with server validation (U12) are built on
these contracts. If an entry point does not work, the units must know which features need a fallback.

## Conclusion

Yes for the client mod in both graphics modes, and with usable vanilla fallbacks:

- **Screens, HUD, toasts, tooltips, world lines, geometry, keys, item renderers in every context (Gui, first /
  third person, ground, item frames, heads) and TF map icons on held and framed maps work identically in Classic
  and Vibrant Visuals.** GUI textures must be drawn as UI meshes (`ui::blit` method 2, the default).
- **Fog**: Classic uses the distance fog, Vibrant Visuals the volumetric air fog (density and scattering from the
  provider's colour and `end`); both come from one `FogSpec`. Cloud height and hidden clouds work in both modes
  through the level renderer.
- **Maps**: decorations are drawn in the space the game uses when it looks a map up; `MapRenderer::render` must not
  be hooked on 1.26.51. Decoration names are not drawn (TF's map decorations have none).
- **Movement validation** works against real clients: validators check the position the client claims before the
  auth input is queued, and the correction runs after the queued move was applied; server teleports, respawns
  and dimension changes start it afresh. Input edges take the ground state from the auth input packet.
- **Native particles**: server-spawned effects reach the client as `SpawnParticleEffectPacket` and do not go
  through `Level::addParticleEffect`; both are hooked, and `gf::fx::particle` reaches companions as F10's
  `fx.particle`, which F12 connects to the factories (`gf::fx::client::setNativeSink`).
- **Keys must be registered from a module's `load()`** (LeviLamina binds them when the game builds its input
  handler, before the modules' `install()`). A key registered later still works with its default key (raw
  `KeyInputEvent`s) with a warning, but is missing from the controls until the next start.

For vanilla clients: forms and DDUI both work and are the screen fallback. Container skins through the chest
JSON-UI are not possible on 1.26.51 (evidence above): `containerTitleSkin` keeps plain titles (`kJsonUiSkins`
is false) and vanilla players see the vanilla container.

## Fallback and follow-ups

- If the UI mesh route breaks after a game update, `ui::setBlitMethod` switches to the image batch; the fixture
  HUD shows the three methods side by side for a quick check.
- Vanilla container skins: a later game version that evaluates `requires` or view bindings with the container
  title would allow a per-title image (the texture route above works); until then DDUI / forms.
- Verified in e2e since round 6: a block renderer on a placed block (the fixture block, lit at its place) and a
  tint on the game's foliage (TF's twilight oak leaves). Not verified in e2e (registry selftests only): entity
  renderer dispatch with real TF content, music, local movement handlers, weather replacement, factory params from molang variables (a `/particle`
  carries none). W1 units that use them (U3, U5, U6, U10, U12, U15) add their own e2e.
- Bedrock still draws its own player marker under the topmost player icon of a magic map (MapRenderer::render
  cannot be hooked); both use the map's (x / 2 + 64, z / 2 + 64) and the same 16 rotations, so the TF icon
  covers it.
- The camera shake is TF's visible beanstalk effect (rotation jitter per tick); TF's per-frame
  `ComputeCameraAngles` jitter never runs in TF either (its tick handler zeroes the intensity first).

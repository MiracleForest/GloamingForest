# S5: Can one F12 client contract drive TF's screens, HUD, world rendering and atmosphere on Bedrock, under Classic and Vibrant Visuals, with vanilla fallbacks?

| | |
|---|---|
| Unit | F12 |
| Status | answered with a fallback (vanilla container skins: no) |
| Date | 2026-11-02 |
| Game / LeviLamina | 1.26.51 / 26.51.7 |

## Question

Do the RenderDragon / UI entry points the F12 contracts need (UI render events, the level renderer's
block-entity pass, item frames, head gear and maps, the sky / fog / weather functions, the tint
resolver, key mappings, the local player's tick, the server's auth input) work in the shipping client
under both graphics modes, so that W1 units can draw TF's GUIs, HUD overlays, toasts, world-space lines
and geometry, item renderers in every context, map icons, skies and fog without hooking the engine
themselves (rule R8)? And do vanilla clients get usable fallbacks (forms, DDUI, JSON-UI container
skins) without companion packets?

## Why it matters

Every TF screen (UncraftingScreen), overlay (ItemDisplayOverlay, ShieldOverlay, QuestingRamIndicator,
PortalOverlay), toast (LockedBiomeToast, MissingAdvancementToast), block / item / entity renderer
(trophies in frames and on heads, casket, red thread, protection boxes), the Twilight sky / fog / aurora /
locked-biome weather (U15), the 29 TF particles, the magic / maze map icons (U13), TF's 4 keybinds
(U11/U12) and the client-authoritative movement modifiers with server validation (U12) are built on
these contracts. If an entry point does not work, the units must know which features need a fallback.

## What was tried

All code is on branch `f12-ui` (contracts `client.ui`, `client.render`, `client.world`,
`client.input+movement` and the server half of `client.ui`; additions in `src/feature/ext/ui/`).

1. **Screens / HUD / toasts / tooltips** (`src/client/ui/Ui.cpp`): `ll::event::AfterUIRenderEvent` on
   `hud_screen` for HUD layers; toasts on the top scene (and in the cancelled `BeforeUIRenderEvent` of a
   framework screen) with Java's ToastComponent slots and the UI sound `random.toast`; `ContainerScreen`
   on the W0a screen framework with the item's whole hover text (`getFormattedHovertext`) as tooltip.
   Three ways to draw a GUI texture compared in the fixture HUD: 0 `drawImage` + `flushImages("ui_flush")`,
   1 the same with `"ui_textured_and_glcolor"`, 2 a `Tessellator` quad drawn with `ui_textured`.
2. **World rendering** (`src/client/render/Render.cpp`): `LevelRendererCamera::$renderBlockEntities`
   (`onWorld`, block renderers tracked in `extractCustomBlock`), `ActorRenderDispatcher::render`,
   `ItemInHandRenderer::renderItem`, `ItemRenderer::$render`, `InventoryItemRenderer::$render` +
   `$endSharedMeshBatch`, **item frames** through `BlockActorRenderDispatcher::render` (both overloads),
   **head gear** through `DataDrivenRenderer_tempComponent_HumanoidAdditionalRendering::_renderHeadGear`,
   **maps** through `MapRenderer::render` and then through `MapRenderer::_getMapInstance` inside
   `ItemInHandRenderer::renderFirstPerson` / `renderItem` / the item frame dispatch; tints in
   `PositionDependentTintResolver::$_get`. Registries are copy-on-write snapshots (no lock on the chunk
   builder threads).
3. **Atmosphere** (`src/client/world/Sky.cpp`): `renderSky`, `LevelRendererPlayer::$setupFog` (distance fog
   **and** the volumetric air fog `mCurrentFogDensity` / `mAirFogCoefficient`), the frame's
   `ViewRenderData` (`mFogColor`, `mDrawClouds`, `mDrawWeather`) and `LevelRendererCamera::mCloudHeight` in
   `LevelRendererCamera::$render`, `$getCloudHeight`, `$tickRain`, `getSituationalMusic`,
   `Level::$addParticleEffect` (molang variables to factory params), `getFieldOfViewModifier`, the camera
   shake as TF's per-tick rotation jitter.
4. **Input / movement** (`src/client/input/Input.cpp`, `src/feature/movement/Movement.cpp`): key handles,
   `LocalPlayer::$normalTick`, and on the server `ServerNetworkHandler::$handle(PlayerAuthInputPacket)`:
   the packet is only queued there (`ServerPlayerMovementComponent::mQueuedUpdates`), so validators now
   check the position the client claims (`PlayerAuthInputPacketPayload::mPos` minus the eye height)
   before it is queued and a rejected move is corrected two ticks later.
5. **Vanilla fallbacks** (`src/feature/ui/Ui.cpp`): forms, DDUI (`ll::ui::CustomForm`), JSON-UI chest skins
   (`ui/chest_screen.json`, removed again). Round 1 tried expressions on `$container_title`; round 2 tried the
   container screen's `#title_text` binding (view bindings for `#visible`, the texture path and the title),
   exact-title and prefix tests in `variables.requires` on the panel and on the screen element, `ignored`, an
   image whose texture is `$container_title`, and diagnostic labels for each.
6. **Fixture** (`src/client/ui/Fixture.cpp`, `src/feature/ui/Fixture.cpp`, development builds only): HUD
   layer, two toasts (LockedBiomeToast's and MissingAdvancementToast's colours), world lines and geometry,
   fog / sky / cloud provider, `ContainerScreen`, the keys `J` (registered at mod load) and `K` (registered
   at install, after the input handler was built), a native particle factory, a named vanilla chest, an
   item frame with `gf_test:fixture_item` (Fixed), `gf_test:fixture_block` on the head (Head), TF-style
   decorations on a held and a framed map (one conquered: TF's red X; the vanilla player icon on top), a
   movement rule, a distance rule across a respawn and the input edges of a jump; driven by `ui.fixture_*`
   from `tools/e2e/client/scenarios/ui.ps1` in Classic (`graphics_mode:1`) and Vibrant Visuals
   (`graphics_mode:2`); the hand is shown for the run (`gfx_hidehand:0`) and restored after. The fixture
   acts on a real player only when it carries the tag `gf_ui_fixture` (the scenario adds it after its
   `ui.*` run, which must leave the untagged player alone); its blocks go on a stage in the ui selftest
   row (`testPos(6260..6262)`, dz 0..4) and `ui.fixture_clear` puts the stage, the player's position, held
   stack and helmet back. Its textures and geometry are built into the mod (`src/client/ui/FixtureAssets.h`),
   written next to the test data and drawn as file textures (`ResourceFileSystem::Raw`), so the resource
   pack carries nothing of the fixture.
7. **Round 3** (review): movement validation starts afresh on `Player::teleportTo` (hooked), on
   `PlayerRespawnEvent`, while the player is dead and on a dimension change, and drops the pending
   corrections then; the ground state of the input edges comes from the auth input packet
   (`VerticalCollision` and the claimed y); the chunk builders' per-`Block*` caches are dropped on every
   level exit and join; toasts carry a style and are not drawn while the GUI is hidden (F1,
   `IOptionRegistry::getHideHud`); `ContainerScreen` states of closed screens are pruned every UI pass;
   late keys are delivered from `ll::event::KeyInputEvent`; map decorations take TF's two
   `IMapDecorationRenderer`s and the vanilla icons of `textures/map/map_icons` (4 x 4 cells of 16 px:
   0 player, 1 frame, 2 red marker, 3 blue marker, 4 the red X, ... 14 mansion, 15 monument).

- Head space: the world matrix the game leaves after `_renderHeadGear` is the head's pose in blocks with y down
  (`0.9354,0,-0.063 | 0,-0.9375,0 | ... | 0.001,-0.206,4` for the player at scale 0.9375): Java's state after

## Conclusion

Yes for the client mod in both graphics modes, and with usable vanilla fallbacks:

- **Screens, HUD, toasts, tooltips, world lines, geometry, keys, item renderers in every context (Gui, first /
  third person, ground, item frames, heads) and TF map icons on held and framed maps work identically in Classic
  and Vibrant Visuals.** GUI textures must be drawn as UI meshes (`ui::blit` method 2, the default).
- **Fog**: Classic uses the distance fog, Vibrant Visuals the volumetric air fog (density and scattering from the
  provider's colour and `end`); both come from one `FogSpec`. Cloud height and hidden clouds work in both modes
  through the level renderer.
- **Maps**: decorations are drawn in the space the game uses when it looks a map up; `MapRenderer::render` must not
  be hooked on 1.26.51. Decoration names are not drawn (TF's map decorations have none).
- **Movement validation** works against real clients: validators check the position the client claims before the
  auth input is queued, and the correction runs after the queued move was applied.
- **Keys must be registered from a module's `load()`** (LeviLamina binds them when the game builds its input
  handler, before the modules' `install()`). A key registered later still works with its default key (raw
  `KeyInputEvent`s) with a warning, but is missing from the controls until the next start.

For vanilla clients: forms and DDUI both work and are the screen fallback. Container skins through the chest
JSON-UI are not possible on 1.26.51 (evidence above): `containerTitleSkin` keeps plain titles (`kJsonUiSkins`
is false) and vanilla players see the vanilla container.

## Fallback and follow-ups

- If the UI mesh route breaks after a game update, `ui::setBlitMethod` switches to the image batch; the fixture
  HUD shows the three methods side by side for a quick check.
- Vanilla container skins: a later game version that evaluates `requires` or view bindings with the container
  title would allow a per-title image (the texture route above works); until then DDUI / forms.
- Not verified in e2e (registry selftests only): block / entity renderer dispatch with real TF content, tints,
  music, local movement handlers, weather replacement, factory params from molang variables (a `/particle`
  carries none). W1 units that use them (U3, U5, U6, U10, U12, U15) add their own e2e.
- Bedrock still draws its own player marker under the topmost player icon of a magic map (MapRenderer::render
  cannot be hooked); both use the map's (x / 2 + 64, z / 2 + 64) and the same 16 rotations, so the TF icon
  covers it.
- The camera shake is TF's visible beanstalk effect (rotation jitter per tick); TF's per-frame
  `ComputeCameraAngles` jitter never runs in TF either (its tick handler zeroes the intensity first).

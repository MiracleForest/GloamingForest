# S5: Can one F12 client contract drive TF's screens, HUD, world rendering and atmosphere on Bedrock, under Classic and Vibrant Visuals, with vanilla fallbacks?

| | |
|---|---|
| Unit | F12 |
| Status | answered with a fallback |
| Date | 2026-11-02 |
| Game / LeviLamina | 1.26.51 / 26.51.7 |

## Question

Do the RenderDragon / UI entry points the F12 contracts need (UI render events, the level renderer's
block-entity pass, the sky / fog / weather functions, the tint resolver, key mappings, the local
player's tick, the server's auth input) work in the shipping client under both graphics modes, so
that W1 units can draw TF's GUIs, HUD overlays, toasts, world-space lines and geometry, skies and fog
without hooking the engine themselves (rule R8)? And do vanilla clients get usable fallbacks (forms,
DDUI, JSON-UI container skins) without companion packets?

## Why it matters

Every TF screen (UncraftingScreen), overlay (ItemDisplayOverlay, ShieldOverlay, QuestingRamIndicator,
PortalOverlay), toast (LockedBiomeToast, MissingAdvancementToast), block / item / entity renderer
(trophies, casket, red thread, protection boxes), the Twilight sky / fog / aurora / locked-biome weather
(U15), the 29 TF particles, the magic / maze map icons (U13), TF's 4 keybinds (U11/U12) and the
client-authoritative movement modifiers (U12) are built on these contracts. If a hook does not fire
under Vibrant Visuals, the units must know which features need a fallback.

## What was tried

All code is on branch `f12-ui` (contracts `client.ui`, `client.render`, `client.world`,
`client.input+movement` and the server half of `client.ui`; additions in `src/feature/ext/ui/`).

1. **Screens / HUD / toasts / tooltips** (`src/client/ui/Ui.cpp`): `ll::event::AfterUIRenderEvent` on
   `hud_screen` for HUD layers and toasts; `ContainerScreen` on the W0a screen framework; tooltips through
   `ItemStackBase::getFormattedHovertext`. Three ways to draw a GUI texture were compared side by side
   in the fixture HUD (`ui::setBlitMethod`): 0 `MinecraftUIRenderContext::drawImage` +
   `flushImages("ui_flush")`, 1 the same flushed with `"ui_textured_and_glcolor"`, 2 a textured quad
   from the screen context's `Tessellator` drawn with `MeshHelpers::renderMeshImmediately` and the
   `ui_textured` material (common group) and the UI context's `TexturePtr`.
2. **World rendering** (`src/client/render/Render.cpp`): `LevelRendererCamera::$renderBlockEntities`
   (opaque pass) for `onWorld` and block renderers (positions recorded in
   `ClientBlockPipeline::WorldExtractorStep::extractCustomBlock`), `ActorRenderDispatcher::render`,
   `ItemInHandRenderer::renderItem`, `ItemRenderer::$render`, `InventoryItemRenderer::$render` +
   `MinecraftUIRenderContext::$endSharedMeshBatch`; `Lines` tessellated as thin bars with the
   `wireframe` material (`ui_fill_gradient` through walls); `drawGeo` parses the packs' `*.geo.json`
   (bones, pivots, rotations, box / per-face UV, mirror, inflate; `src/client/render/Geo.cpp`) and draws
   with the moving-block alpha-test material and the geometry's own texture;
   `PositionDependentTintResolver::$_get` for tints.
3. **Atmosphere** (`src/client/world/Sky.cpp`): `LevelRendererCamera::renderSky`,
   `LevelRendererPlayer::$setupFog` (+ the frame's `ViewRenderData::mFogColor` in
   `LevelRendererCamera::$render`), `Dimension::$getCloudHeight` / `OverworldDimension::$getCloudHeight`
   on the client level, `LevelRendererPlayer::$tickRain`, `MusicManager::getSituationalMusic`,
   `Level::$addParticleEffect` (native particle factories), `LocalPlayer::getFieldOfViewModifier`,
   `CameraShakeComponent::queueShakeEvent`.
4. **Input / movement** (`src/client/input/Input.cpp`, `src/feature/movement/Movement.cpp`):
   `ll::input::KeyRegistry` key handles (forwarded to the server on `input.key`),
   `LocalPlayer::$normalTick` for the local movement handlers,
   `ServerNetworkHandler::$handle(PlayerAuthInputPacket)` for input edges and move validation,
   `SetActorMotionPacket` for motion.
5. **Vanilla fallbacks** (`src/feature/ui/Ui.cpp`): `ll::form::SimpleForm`, `ll::ui::CustomForm`
   (DDUI), and a JSON-UI modification of the vanilla chest screen (`ui/chest_screen.json`) that was to
   read a skin marker from the container title — first by slicing `$container_title`
   (`('%.40s' * ($container_title - 'gfskin:'))`), then by removing a whole known marker
   (`($container_title - 'gfskin:<id>;')`).
6. **Fixture** (`src/client/ui/Fixture.cpp`, `src/feature/ui/Fixture.cpp`): a HUD layer, a toast, world
   lines and the fixture geometry, a fog / sky / cloud provider, a `ContainerScreen` with an original
   GUI skin in TF's container layout (176 x 166, slots at Java's positions), the fixture key `J`, a
   vanilla chest; driven by the selftests `ui.fixture_*` from `tools/e2e/client/scenarios/ui.ps1`, once
   with `graphics_mode:1` (Fancy, "Classic") and once, after a game restart, with `graphics_mode:2`
   (Advanced, "Vibrant Visuals"); `ui.prelaunch.ps1` / `ui.restore.ps1` set and restore the instance's
   setting.

## Conclusion

Yes for the client mod, with three limits:

- **Screens, HUD, toasts, world lines, geometry, keys and the native screen actions work identically in
  Classic and Vibrant Visuals.** GUI textures must be drawn as UI meshes (`ui::blit` method 2, the
  default); the UI image batch (`drawImage` / `flushImages`) renders black in this version.
- **Distance fog and cloud height only take effect in Classic.** Under Vibrant Visuals the hooks run but
  the deferred pipeline renders its own volumetric fog and clouds. U15 must also ship data-driven fog
  (`fogs/*.json` per biome, which both modes and vanilla clients read) and treat the provider fog as the
  Classic refinement; the sky provider (`renderSky`) is called in both modes.
- **Keys must be registered from a module's `load()`**; `registerKey` warns when called in a running game.

For vanilla clients, forms (and DDUI where the client supports it) are the screen fallback. The JSON-UI
container skin does not work on 1.26.51: `containerTitleSkin` therefore keeps plain titles
(`kJsonUiSkins` is empty) and vanilla players see the vanilla container.

## Fallback and follow-ups

- If the UI mesh route breaks after a game update, `ui::setBlitMethod` switches to the image batch;
  the fixture HUD shows the three methods side by side for a quick check.
- Not verified in e2e (selftests cover the registries only): block / entity / item renderer dispatch
  with real TF content, tints (the hook adds `mMinPos` to the resolver's position), music, native
  particle dispatch from `Level::addParticleEffect`, map views, camera shake, local movement handlers,
  weather replacement. W1 units that use them (U3, U5, U6, U10, U12, U13, U15) add their own e2e.
- Not implemented: custom map icons are registered and kept per map but no `MapRenderer` overlay draws
  them yet; item renderers for `Fixed` / `Head` contexts are never dispatched.
- JSON-UI container skins: retry with a binding-based JSON-UI (a container title binding, if one
  exists) and list the skins in `kJsonUiSkins`; until then DDUI / forms.
- Vibrant Visuals fog: investigate `LevelRendererCamera::mCurrentFogDensity` / the volumetric fog
  coefficients (`_getCurrentCoefficientFogSetting`) as the VV counterpart of the distance fog.

# S7: Can TF's assets and data be converted automatically into a Bedrock content skeleton that loads cleanly?

| | |
|---|---|
| Unit | F1 |
| Status | answered |
| Date | 2026-11-02 |
| Game / LeviLamina | 1.26.51 / 26.51.7 |

## Question

Can one deterministic tool turn The Twilight Forest 4.8's textures, blockstates, Java block / item models, lang
files and data into Bedrock behaviour / resource packs in which every TF id exists (523 blocks with their states,
254 items plus the block items and 51 spawn eggs, 80 entities), within the block permutation budget, such that
BDS 1.26.51 loads the full skeleton with **zero content-log errors**, the client renders the blocks and items, and
the generated tree is reproduced byte for byte on another machine (`-Check` in CI)?

## Why it matters

R1 requires every TF id to exist from W0 so that W1 units can reference each other by string (R2) and merge in any
order; the frozen block states (blockstates.md) are the contract every block owner builds on; the dangling-reference
and owner checks of assemble need a complete id set; and the content log must stay clean or every later e2e fails.
Consumers: every W1 unit (their `assets/gen/import/<u>/**`), F9 (recipes, tags, data maps, catalog), F10 (loot,
damage types), F11 (families, blockstates), F6 (structure descriptors), F3 (sound-event listing; F3 itself writes
the `sound_definitions`, the import emits none), F12 (particles).

## What was tried

1. **Tooling.** A C# importer (`tools/import/src`, compiled by `tools/import/run.ps1` through `Add-Type`, cached by
   source hash): own order-preserving JSON writer and PNG encoder (fixed-Huffman DEFLATE) so the output does not
   depend on the .NET / zlib version; TF text read with line endings normalised (the checkout is CRLF on CI). A full
   import of 7.2k files takes about 3 s.
2. **Blocks.** The Java properties of every block's class chain (`createBlockStateDefinition` of each TF class,
   following `super`, plus the vanilla base's full set; constants resolved to `Property.create` names, ranges and
   enum values) -> `twilightforest:<prop>` states (integer lists from 0, booleans, enums with TF's default first;
   `waterlogged` dropped), checked against a hand-written golden (`tools/import/expected-states.json`) and TF's
   blockstate files. Variants -> permutations with Molang conditions and `minecraft:transformation`; multipart ->
   one geometry with a bone per part and Molang `bone_visibility`. Java models (2984 generated + 123 hand-made)
   resolved through their parents; the vanilla parent shapes (stairs, slabs, fences, gates, doors, trapdoors,
   buttons, plates, crosses, flower pots, panes, fire, ...) come from a built-in library; element sets become
   shared Bedrock geometries (`geometry.tf.<model>`, material instances named after the Java texture variables),
   single full cubes use `minecraft:geometry.full_block`; every permutation of a rotated block states its rotation
   (checked for all 3659 variants against TF's blockstates). Hardness / resistance as Java's
   `BlockBehaviour.Properties` computes them (defaults 0, call order, products of literals, `ofFullCopy` and
   `copyAndScaleProperties` copies of TF and vanilla blocks, registration helpers with their arguments), TF's
   `setFlammable` flammability, and state-dependent values evaluated per permutation: light (lambdas and
   `getLightEmission`), explosion resistance and destructibility (`getExplosionResistance` /
   `getDestroyProgress` overrides), map colour (lying logs, castle doors). Booleans list TF's default first.
   Tools and drops: TF's `#minecraft:mineable/*`, `#minecraft:sword_efficient`, `#minecraft:leaves` and
   `#minecraft:needs_*_tool` tags (with the vanilla 1.21.1 tags they reach) become Bedrock's tool and tier block
   tags (`minecraft:is_pickaxe_item_destructible`, `minecraft:diamond_tier_destructible`, ...);
   `requiresCorrectToolForDrops()` blocks are listed in `data/gf/import/harvest.json` and get the engine's
   requires-correct-tool flag at run time (`src/feature/ext/import/Harvest.cpp`), which JSON blocks cannot declare.
   Format 1.21.80 (W0c: 1.26.50 with the `minecraft:tags` array, the family blocks 1.21.80; W0d: every block 1.26.50; see the follow-ups below).
3. **Items / entities.** Items with icons, stack sizes and durability (tool tiers, armour types, by class chain), hand-equipped, TF item tags, and for the tiered tools Bedrock's tool tags and a `minecraft:digger` from the tier's speed; block items whose
   Java item model is flat -> `minecraft:block_placer` + `replace_block_item`; entities with collision boxes,
   health parsed from `createAttributes`, `is_spawnable` + client `spawn_egg` colours for TF's 51 eggs; placeholder
   client entities (a box of the entity's size with its TF texture).
4. **Recipes.** Vanilla types -> Bedrock recipes with `unlock` from the recipe advancements; tags expanded or kept
   (Bedrock-native and TF-item-only tags).
5. **Catalog.** TFCreativeTabs -> `crafting_items_catalog` groups.
6. **Selftests** (`src/feature/ext/import/ImportTests.cpp`): `import.blocks` (every block registered, every frozen
   state present with the expected default), `import.items` (864 item ids), `import.entities` (80 definitions),
   `import.lang_and_data`, `import.place_blocks` (all 523 blocks placed and read back), and, independent of the
   generator: `import.java_states` (states written down from TF's classes), `import.rotations` (per-state rotation of
   the assembled block files against TF's blockstates), `import.light` (the game's light emission per state),
   `import.behaviour` (the game's destroy speed and explosion resistance per state against TF's values, calibrated
   on vanilla blocks), `import.bool_defaults` (a `[true, false]` boolean defaults to `true`) and
   (`src/feature/ext/import/HarvestTests.cpp`) `import.harvest_tags` (every block's tool / tier tags and drop flag
   in game), `import.harvest_mining` (a survival player's destroy progress and the tools' harvest decision on TF
   blocks against vanilla blocks and tools of the same Java values) and `import.harvest_drops` (blocks broken by a
   survival player drop only for a correct tool).

## Evidence

- `pwsh tools/import/run.ps1 -Check`: every generated file identical (about 7.2k files, 13.5 MB) locally (pwsh 7.6 /
  .NET 10) and on the CI runner (windows-latest, a fresh TF checkout fetched by the tool): byte-for-byte determinism
  across machines and .NET versions.
- `pwsh tools/assemble.ps1 -Check`: OK, 6638 block permutations, every generated file owned, every
  `twilightforest:` reference known.
- Server e2e `import` (BDS 1.26.51, exit 0): `SELFTEST DONE pass=10 fail=0` (the scenario requires each of the 10
  `import.*` tests by name); `import.blocks` 523 blocks with their frozen states and defaults, `import.items` 864
  item ids, `import.entities` 80 definitions, `import.place_blocks` 523 blocks placed and read back;
  **0 content-log errors and 0 content-log warnings** (per-permutation `destructible_by_mining`,
  `destructible_by_explosion` and `map_color` are accepted). Server e2e `full`: `pass=28 fail=0`.
- Boolean defaults: Bedrock 1.26.51 takes the first listed value of a boolean state as its default and reads the
  value, not the position: with `twilightforest:powered: [true, false]` the default permutation of the trophies
  has `powered=true`, `{powered: true}` is that permutation and `{powered: false}` another one
  (`import.bool_defaults` on 7 blocks), and the explosion permutation conditioned on `!locked` applies to the
  unlocked states only (`import.behaviour`: the default locked vanishing block resists `Float.MAX_VALUE`, the
  unlocked ones 6000 / 2000).
- Behaviour units: the game stores vanilla blocks at Java's values (`minecraft:oak_planks` 2.0 / 3.0, `stone`
  1.5 / 6.0, `obsidian` resistance 1200; Bedrock's own obsidian hardness is 35, Java's 50) and a JSON block's
  destroy speed as `seconds_to_destroy` (-1 for `destructible_by_mining: false`) but its explosion resistance as a
  **fifth** of `explosion_resistance` (3 -> 0.6, 50 -> 10, 6000 -> 1200; FLT_MAX / 5 for `false`). An earlier
  round wrote Java's resistance unchanged and calibrated `import.behaviour` on a TF block, which hid the factor: TF
  blocks then resisted explosions 5 times less than the vanilla blocks of the same Java value. The import now
  writes Java's resistance x 5 and `import.behaviour` calibrates on the vanilla blocks: `twilight_oak_planks` reads
  2.0 / 3.0 as `minecraft:oak_planks`, `underbrick` 1.5 / 6.0 as `minecraft:stone`, `castle_brick` 100 / 50, every
  drying rack 1.0 / 1.5, the brazier 0 / 0, the berry bushes 0.4 / 0.
- Tools and drops, measured in game against vanilla blocks and tools (`import.harvest_*`, server e2e `import`
  pass=13 fail=0): with the tool / tier tags and the requires-correct-tool flag, a survival player's destroy
  progress on `underbrick`, `knightmetal_block`, `castle_brick`, `twilight_oak_planks`, `twilight_oak_leaves` and
  `uberous_soil` equals that on `iron_ore`, `diamond_block`, `obsidian`, `oak_planks`, `oak_leaves` and `dirt` (per
  stored hardness) for the hand and the vanilla pickaxes, axes, hoes and shovels; knightmetal / steeleaf tools mine
  as diamond ones, fiery as netherite. Broken by a simulated survival player, `underbrick` drops nothing for a
  wooden pickaxe and drops for a stone or giant pickaxe, `knightmetal_block` nothing for a stone pickaxe and drops
  for an iron or ironwood one, as the vanilla controls (`iron_ore`, `diamond_block`) do. The engine's flag reads
  true on vanilla stone and obsidian and false on dirt, and true on the 90 TF blocks that require a correct tool.
  Two measured engine limits: a custom item harvests every block its digger lists whatever its tier tags (the
  digger leaves out higher-tier blocks instead), and vanilla shears and swords single out their own leaves by
  block type (on TF's leaves the shears mine at 5, a sword at 1; Java 15 and 1.5).
- Bedrock's `minecraft:digger` takes integer speeds only: 1.26.51 logs `minecraft:digger -> destroy_speeds[n] ->
  speed: invalid numeric value` for 6.5 (ironwood) and 1.5 (a sword's `sword_efficient` rule); the import rounds
  half up (7, 2) and lists the 12 tools in its log.
- The first BDS run had 507 content-log errors, all in recipes (blocks, items and entities had none).
- First BDS run findings, fixed in the importer: `"unlock": [{"context": "AlwaysUnlocked"}]` is rejected ("Recipe
  ingredient is invalid", "invalid unlock ingredient"): the context form is an object, `"unlock": {"context":
  "AlwaysUnlocked"}`; Bedrock measures shaped-recipe rows in bytes, so TF's non-ASCII pattern keys (`∴`, `•`)
  must be remapped to ASCII; Java `minecraft:*` item tags on custom items carry engine meaning on Bedrock (TF's
  `minecraft:trim_materials` members make the vanilla trim recipe log an error), so only TF / `c:` tags are put on
  items; items listed in the crafting catalog log a warning unless their `menu_category` names the catalog's
  category.
- Blocks, items and entities produced **no** content-log error on the first run: block states (up to 16 values),
  permutations with Molang conditions, `bone_visibility` with Molang, `replace_block_item`, the crafting catalog
  and custom entity definitions are all accepted by 1.26.51.
- Client e2e `import` (local, exit 0): `blocks-row.png` shows TF's textures on full cubes, stairs, slab, fence
  post, leaves, the sapling cross, door, trapdoor, firefly jar and the uncrafting table; `creative-search-twilight.png`
  lists TF's items with their icons (flat icons for signs and saplings via `replace_block_item`). The first client
  run showed black spawn eggs for 9 entities TF registers without an egg (egg colours 0): the import now gives
  eggs only to the 51 entities owners.tsv lists. `creative-construction-tf.png`: TF's blocks group ("Twilight Forest:
  Blocks", localised through the texts key `twilightforest:itemGroup.twilightforest.blocks`) at the end of the
  construction category, TF's order.
- Client e2e `import` `-Mode remote-vanilla` (exit 0): a client without the mod joins the BDS host, downloads the
  packs and renders the same block row and creative pages: the skeleton needs no client mod.
- Geometry conventions (checked against Blockbench's Java -> Bedrock export): cube origin `[8 - to.x, from.y,
  from.z - 8]`, element rotation `[-x, -y, z]`, up / down face UVs flipped; blockstate rotation as
  `minecraft:transformation` `[-x, -y, 0]` (Bedrock's cardinal-direction convention: east is `-90`).

## Conclusion

Yes. The skeleton is generated entirely from TF's checkout, loads in BDS without content errors, and is checked
in game by the `import.*` selftests. Chosen design:

- generated layer `assets/gen/import/<unit>/**` partitioned by owners.tsv, regenerated by the tool only;
  overrides per unit; the manual layer overrides per id;
- frozen block states = Java property names under `twilightforest:`, no placement traits (placement is behaviour,
  F11 / owners), `waterlogged` not a state;
- shared geometries for vanilla shapes, multipart blocks as bone-visibility geometries;
- TF data kept in Java format by id (loot, recipes, advancements, worldgen, registries, tags, data maps) for the
  runtime contracts; only vanilla-type recipes are converted to Bedrock recipes.

Limits: models without elements (block entity renderers: chests, trophies, skull candles, casket, ...) render as
a cube with their particle texture until their owner adds a renderer; the mason jar's light (from its block entity), biome tinting of
leaves / grass, `uvlock`, random model variants and connected textures are left to the owners (F11, F12, W1);
entity visuals are placeholders until F2's geometry and the owners' render controllers land; vanilla clients see
the same packs (no client-mod dependency in the skeleton).

## Fallback and follow-ups

- If a later game version rejects a component, the tool changes in one place and `-Check` regenerates every unit.
- The ownership manifest does not list `assets/gen/import/<w1 unit>/**` or `tools/e2e/*/scenarios/import*.ps1`
  for F1 (they belong to the W1 units / F0), so `tools/ci/ownership.ps1 -Unit F1` reports those generated paths;
  F0 should let the tool owner write `gen` paths (see the PR).
- assemble's dangling-reference check treats every `twilightforest:` string in TF's Java data as an id reference;
  TF data names code-registered types, texture locations and custom-registry tags. The import resolves every
  reference itself against a reviewed allowlist (`tools/import/known-ids.json`, kind + reason + TF source) and fails
  on an unknown one. W0b bridged assemble with an index file per resolved reference (`data/twilightforest/gf_known/**`);
  since F0's W0c (issue #21) assemble reads the allowlist itself, and the bridge is gone (W0c, below).
- W1 owners refine their generated files only through `tools/import/overrides/<u>.json` or manual files.

## W0c follow-up: block tags in the block formats of 1.26.51 (2026-11-02)

**Question.** F11 found that a block file in format 1.26.50 refuses the `"tag:<id>": {}` components the import
writes ("this component was found in the input, but is not present in the Schema"), so TF's chest families cannot
take `minecraft:block_entity` (which 1.26.0 refuses, "not valid here", and 1.26.50 takes; spike S3), the component
F10's native container backend needs (and with it hoppers, which work on TF's chests in Java). How does a block of
format 1.26.50, or the newest format BDS 1.26.51 accepts, declare block tags?

**What was tried.** The server scenario `import.s7` (`tools/e2e/server/scenarios/import.s7{,.prelaunch}.ps1`, an
evidence run: the forms a format refuses log content errors, so it exits 1 by design) installs a throw-away pack of
35 probe blocks `gf_s7:<form>_<format>`: each of the formats 1.21.80, 1.26.0, 1.26.10, 1.26.20, 1.26.30, 1.26.40 and
1.26.50 with the tags `minecraft:is_pickaxe_item_destructible` and `gf_s7:probe` as `"tag:<id>": {}` components
(`legacy`), as `"minecraft:tags": {"tags": [...]}` (`object`, the item component's form), as `"minecraft:tags": [...]`
(`array`), and `legacy` / `array` with `minecraft:block_entity`; the prelaunch lists every probe it writes in the
pack's `probes.json` (`{"probes": [{id, form, format}]}`), the single list the selftest probes. The selftest
`import.s7_probe` (`src/feature/ext/import/S7Probe.cpp`, server build) reads the name of the 1.26.20 block schema's tag component
(`SharedTypes::v1_26_20::BlockDefinition::Tags::NameId()`, MCAPI) and, per probe, whether it registered, the tags of
its block type and default permutation (`BlockType::mTags`, `hasTag`) and its block actor type. The same run replaces
the families kit's file of each of the 347 family blocks in the slot with the import's own skeleton converted to
1.26.50 (`"tag:"` components -> one `minecraft:tags` array), so all 523 TF blocks load from the import's skeleton at
1.26.50, and runs `import.blocks`, `import.harvest_tags`, `import.rotations`, `import.light` and `import.behaviour`.

**Evidence** (BDS 1.26.51, `tools/e2e/server/out/import.s7/server.log`):

- `SELFTEST INFO import.s7_probe: block schema v1_26_20 tags component: 'minecraft:tags'`.
- Formats 1.26.20 to 1.26.50 (the `SharedTypes::v1_26_20::BlockDefinition` schema; the LeviLamina headers have no
  later block schema): `array` registers, type tags `[minecraft:is_pickaxe_item_destructible, gf_s7:probe]`,
  `hasTag(minecraft:is_pickaxe_item_destructible)` true; `object` fails, `-> components -> minecraft:tags: expected an
  array` (not registered); `legacy` fails, `-> components -> tag:minecraft:is_pickaxe_item_destructible: this component
  was found in the input, but is not present in the Schema` (not registered); `array` + `minecraft:block_entity`
  registers with its tags and block actor type 62 (`DataDrivenBlockActor`, as in S3).
- Formats 1.21.80, 1.26.0 and 1.26.10 (the legacy parser): `legacy` registers with both tags; `object` and `array`
  fail, `components | minecraft:tags | child 'minecraft:tags' not valid here. ... Block definition parsing failed`;
  `minecraft:block_entity` fails in any form, `child 'minecraft:block_entity' not valid here`.
- The whole skeleton at 1.26.50: no content-log error and no warning for any of the 523 TF blocks (the only errors of
  the run are the refused probe forms above; BDS's own transport notice aside), `import.blocks` 523 blocks with their
  frozen states OK, `import.harvest_tags` 387 blocks with their tool / tier tags as the game holds them (90 drop only
  for a correct tool), `import.rotations`, `import.light`, `import.behaviour` pass. The first such run had one other
  component error, on the only non-family multipart block whose parts are all unconditional (`ominous_fire`):
  `minecraft:geometry -> bone_visibility -> part0: invalid string ... expected an object ... invalid numeric value`:
  the v1_26_20 schema takes a Molang string (no boolean `true`); the import now leaves an unconditional part out of
  `bone_visibility` (a bone it does not name is shown).
- With the import's output (the 176 blocks loaded as written at 1.26.50 with the `minecraft:tags` array, the 347 family
  blocks at 1.26.0 from the kit): server `import` exit 0, `SELFTEST DONE pass=14 fail=0`, 0 content-log errors and
  warnings (`import.place_blocks`: 523 blocks placed with their support and read back; `import.harvest_tags` 387
  blocks); server `full` pass=290 fail=2 (`dimension.portal_block` and `structure.processors`, F4's and F7's known
  failures; every `import.*` and `families.*` test passes); client `import` local exit 0 (pass=13 fail=0, the block
  row and creative pages as before) and `-Mode remote-vanilla` exit 0 (a client without the mod joins the BDS host,
  downloads the packs and renders the same row and pages). `import.s7_probe` checks the forms above whenever the
  probe pack is installed.

**Conclusion.** From format 1.26.20 a block declares its tags as **`"minecraft:tags": ["<tag>", ...]`** (an array; the
item component's `{"tags": [...]}` is refused), and that format also takes `minecraft:block_entity`; up to 1.26.10 a
block declares them as `"tag:<tag>": {}` components and takes neither `minecraft:tags` nor `minecraft:block_entity`.
No format takes both forms, so a block file's tag form follows its format. Every component the import writes loads
at 1.26.50 (the whole skeleton, evidence above).

**Decision.** The import writes every block the game loads as written in **1.26.50** with the `minecraft:tags` array
(`Blocks.BlockFormat`, `Harvest.HarvestTags`). The 347 family blocks are not loaded as written: F11's families kit
rewrites them at assemble in its own format 1.26.0 (`tools/families/families.lua` `FORMAT`), from a copy of the
skeleton (the shapes it keeps) or from the skeleton's `"tag:"` components (the shapes it draws: signs, chests,
connected textures), and 1.26.0 refuses `minecraft:tags`. Writing them at 1.26.50 now would drop the tool tags of
every family block (measured: an assemble with them at 1.26.50 left the kit's chests and signs without tags and its
stairs at 1.26.0 with a `minecraft:tags` that 1.26.0 refuses), so their skeleton, the kit's input, keeps 1.21.80
with `"tag:<id>"` components (`Blocks.FamilyBlockFormat`) until the kit no longer reads the skeleton's tag form
(it takes `params.tags` instead, below).

**Path for F11** (the chests' `minecraft:block_entity`): the families data carries every family block's Bedrock
block tags free of any format, **`params.tags`** (`data/gf/families/<unit>.json`, `Skeleton.ImportFamilies` from
`Harvest.BedrockBlockTags`: the tool tags and, for a block a tool mines, its tier tag; absent for a block without
tags). It is the single source of a family block's tags: after the overrides the import rewrites the skeleton
file's tags from it in the form of the skeleton's format (`Ctx.SyncFamilyTags`; a unit overrides a family block's
tags by patching `params.tags`, and a patch of the skeleton's tags fails the import), and `CheckEmittedBlocks` fails
when the two still differ. For example `twilightforest:twilight_oak_chest`:
`"params": {..., "tags": ["minecraft:is_axe_item_destructible"]}`. The kit takes the tags from there and writes them
in the form of the format it writes the block in: `minecraft:tags = params.tags` (one array) for a document in
1.26.20 or later, `"tag:<id>": {}` per tag for one up to 1.26.10; it drops whatever tag form the skeleton copy carries
(both `"tag:*"` keys and `minecraft:tags`), so the skeleton's own format no longer matters to it. For the chests that
is: write their documents in 1.26.50 with `minecraft:tags = params.tags` and `minecraft:block_entity` (probe
`array_entity_1_26_50`: tags kept, block actor type 62; `import.s7.prelaunch.ps1` converts the 347 family files the
same way, and they load without error and keep their tags in game). Once the kit no longer reads the skeleton's tag
form, F1 sets `FamilyBlockFormat = BlockFormat`, and that change is a no-op for the kit: the skeleton's tag form
follows its `format_version` (`Ctx.ModernBlockFormat`, used by `HarvestTags` and `SyncFamilyTags`), not a comparison
with `BlockFormat`. Tracked follow-up (two steps, in this order): F11 changes `families.lua` `base_doc` to drop both
tag forms of the skeleton copy and write `params.tags` in its document's form; then F1 flips `FamilyBlockFormat`.

### W0d follow-up: the family blocks at 1.26.50

F11's families kit (PR #32, `tools/families/families.lua`) now drops both tag forms of the skeleton copy in
`base_doc` and writes the entry's tags (`block_tags`: `params.tags`, plus `params.tool`'s tag) in its document's form
(`write_tags`), last, after the behaviours have set the document's format. Its own copy of TF's sound types is gone
as well. So F1 set **`FamilyBlockFormat = BlockFormat`** (1.26.50): every block file the import writes is now 1.26.50
with the `minecraft:tags` array, the 347 family skeletons included.

**Evidence.** The import regenerated 347 files (format and tag form only). `tools/assemble.ps1 -Check` passes, and an
assemble before and after the change gives semantically identical JSON for every family block of the main pack (the
kit's minified output only reorders keys); the remaining differences are in the test pack's `gf_test` fixtures, which
the import does not touch. Server (BDS 1.26.51): `import` pass=15 fail=0 (with `import.sound_types`, which now
requires the jar's jump and land to be `""` in the assembled `sounds.json`), `families` passes, `full` pass=355
fail=0, no content-log error. Client local: `families` passes (its content log has one verbose vanilla sound line); `import` runs its selftests at
pass=14 fail=0 and renders the block row and creative pages (family stairs, banisters, chests and signs included),
and its game writes no content-log file at all: the game creates the file only for its first entry, which the
harness's check reads as "content log did not take effect" (reported to F0).
`import.s7.prelaunch.ps1` still loads the import's skeleton in place of the kit's files (no conversion needed now).

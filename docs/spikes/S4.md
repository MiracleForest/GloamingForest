# S4: Can TF's entities, multipart bosses and RGB boss bars be built on Bedrock with linked actors?

| | |
|---|---|
| Unit | F8 |
| Status | answered with a fallback (multipart, properties, hit test, vanilla bar colour); exact-RGB bar rendering and converter output open |
| Date | 2026-11-02 |
| Game / LeviLamina | 1.26.51 / 26.51.7 |

## Question

Can F8 give TF's 80 entity types their Java behaviour on Bedrock without engine-side entity classes:
native behaviour dispatch on BP entities, persisted per-entity state, entity properties that drive
the Molang of the resource pack, Java's goal selector, TFPart multipart bosses as linked actors
(parts that follow, take hits for the parent and are picked by the client), and TF's RGB boss bar
(exact colour with the client mod, the nearest of the 8 vanilla colours on vanilla clients)?

## Why it matters

Every mob and boss unit (U16-U17, U20-U30) builds on `gf::entity`, `gf::projectile` and
`gf::boss`. The hardest models are the multipart bosses: the Hydra (body, 3-7 heads with necks),
the Naga (12 segments), the Snow Queen (4 ice shields) and the Ur-Ghast; TF's `PartEntity`
needs three ASM patches on Java (ResolveEntitiesForRendering, ResolveEntityRenderer,
SendDirtyEntityData). The boss bar colour (TFBossBarPacket) is a visible difference on every boss.

## What was tried

1. **Behaviour dispatch** (src/feature/entity/Entity.cpp): one hook per engine event, owned by F8
   (rule R8): `Actor::tick` (behaviour tick, goals, aiStep, parts, mounts, the internal hooks of
   the projectile and boss kits), `Mob::$die`, `Actor::save` / `Actor::$load` (the
   `data(actor, key)` documents travel in the actor's own save tag `GloamingForest`, so they
   follow chunk unloads, reloads and dimension changes), `Mob::$setTarget` (target filters).
   Damage reaches `Behaviour::hurt` through `gf::combat` (F10 owns the hurt hook), right-clicks
   through `gf::interactions` (F0).
2. **Entity properties** (`setProperty`): `ActorPropertyUtils::tryQueueVariantValue` on the
   actor's `PropertyComponent` (hash of the property name), applied at once with
   `Actor::_applyPendingPropertyChanges`; read back with `PropertyContainer::getValueVariant`.
   Server-side `Actor::evalMolang("query.property(...)")` is refused by the engine ("not allowed
   in this context", content-log errors): the server evaluates Molang only in restricted contexts.
3. **Goal adapter** (Goals.cpp): Java's `GoalSelector` (insertion order, flags MOVE / LOOK / JUMP /
   TARGET, priorities, interruption, full selector ticks every other tick) runs on F8's tick hook;
   the goals drive the engine's own `NavigationComponent` (`PathNavigation::moveTo / stop`, path
   state), `LookControlComponent` and the mob's motion. The engine's `GoalSelectorComponent` /
   `BaseGoal` were not subclassed: a game-side vtable is ABI-fragile and a pure C++ selector
   reproduces Java's order exactly. TF's nine shared goals and `NoClipMoveControl` are
   translated; `DefaultRandomPos` / `RandomPos` with them.
4. **Linked multipart** (Multipart.cpp): every part is a real actor, `<parent id>_part` when the
   parent's unit declares one (with an integer property `<ns>:part` = the part index for its
   geometry), else F8's invisible `gloamingforest:part`. The parent moves its parts every tick
   (`Actor::moveTo`: clients interpolate as for any moved actor); the size is the part's collision
   box (`Actor::synchronousSetSize`, synced by the engine). A player's attack on a part becomes the
   player's attack on the parent (`interactions::onAttack` at High priority, `Player::attack` on the
   parent with the part id readable through `ext::hurtPart()`); all other damage is forwarded by a
   `gf::combat` handler. Parts are never saved (Java's are not either). Companion clients get the
   part list ("entity.multipart").
5. **Custom hit test**: the client picks a part by its actor AABB (the size set above); the
   parent's `HitboxComponent` (`minecraft:custom_hit_test`) was not needed, so a part keeps its own
   pick box per part. With the Hydra's 7 heads this means 1 + 7 + necks actors, all non-saving,
   physics-free.
6. **Boss bar** (Boss.cpp): F8 sends the bar itself (no `minecraft:boss` component on TF bosses):
   `BossEventPacket` add / update_percent / update_name / update_style / remove per viewer (players
   within 160 blocks, Java's tracking), `mColor` = the nearest of Bedrock's 8 `BossBarColor`s to the
   boss's RGB (redmean distance). Companions also get "boss.bar" {rgb, overlay, darken, fog}; the
   client mod (src/client/entity) tried to write the exact RGB into the HUD's boss table
   (`ClientInstanceScreenModel::mBossInfo`, `BossInfo::mBarColor`), first from hooks on
   `getBossBarColor` / `getBossHealthPercentage`, then after `HudScreenController::$tick`. Both
   crashed the game silently right after the first bar: the generated header's offset of
   `mBossInfo` is wrong in 26.51.7 (a guarded run read a table of 1721291456096 entries). The write
   is now guarded (size and colour layout checked first, disabled with a warning otherwise).
7. **Converter output on 3 models**: F2's `tools/models/convert.ps1` is still F0's stub on main,
   so no converted TF model could be loaded in this spike. The fixtures (`gf_test:boss`,
   `gf_test:boss_part`) use vanilla zombie geometry.

## Evidence

- Server e2e `tools/e2e/server/run.ps1 -Scenario entity` (first run, before the test fixes): 11 of
  13 selftests passed at once: `entity.multipart` (3 parts of type `gf_test:boss_part` with
  `gf_test:part` = 0, 1, 2 follow the parent within 0.6 blocks after a 3-block teleport; a
  SimulatedPlayer's hit on a part lowered the parent's health and not the part's; `Actor::save` of
  a part returns false; the parts are gone two ticks after the parent), `entity.boss_lifecycle`
  (BossEventPacket `add` with colour 2 = red for the orange fixture bar, `update_percent` after the
  hit on a part, the attacker in `participants`, the loot buffer in a vanilla chest under the home
  point: `boss: death chest of gf_test:boss at 50 -60 133 (1 stacks)`, the conquest request
  `boss: gf_test:boss conquered gf_test:fixture`), `entity.boss_peaceful` (`turned back into
  gf_test:fixture_block`, then `gf_test:fixture_block spawned gf_test:boss`), `entity.goals`,
  `entity.mount` (`minecraft:horse grabbed` / `threw`), `entity.multipart_generic`. The two
  failures were test faults (the Molang probe above; a projectile target removed by the peaceful
  rule) and are fixed; the final runs are listed in the PR.
- The property probe: `setProperty(boss, "gf_test:phase", 2)` reads back as int 2.
- Client e2e (`-Mode local`, PASSED with the guard): boss-bar-local.png and boss-parts-local.png
  show the fixture bars in red, the nearest vanilla colour to #FF8000, on the client build; the
  companion received the exact RGB (`client boss bar ... received (#FF8000)`), the guard logged
  `client boss bar colours disabled: the HUD's boss table looks wrong`. The bisect run without the
  write kept the game alive; the two runs with it lost the game within a second of the bar.

## Conclusion

Yes, with these limits:

- **Multipart as linked actors works** on the server build, the client build and vanilla clients
  (parts are ordinary actors): follow, hit routing, removal and non-persistence are verified. The
  risk is network load (one MoveActor per part per tick) and desync under lag; the Hydra (≤ 22
  actors) and Naga (13) stay well within the engine's limits. A8 runs the multiplayer soak.
- **Properties drive the RP's Molang**: units declare their animation state as entity properties
  (int / float / bool / enum, ≤ 32 per entity, `client_sync`), F8 sets them natively; the server
  cannot evaluate `query.property` itself (render controllers and animation controllers on the
  client can). Molang translation of TF's Java animations stays with F2's converter.
- **Boss bar**: the nearest of 8 colours works on every client (verified on the client build).
  Exact RGB reaches the client mod but is not painted yet: the HUD's boss table cannot be reached
  safely through the generated headers. The darken / fog flags reach companions only (the 26.51
  `BossEventPacket` carries neither).
- **Goals**: Java's selector semantics exactly; navigation is Bedrock's pathfinder (path shapes
  differ from Java's), `getWalkTargetValue` is 0 for every mob (vanilla Monsters prefer darker
  spots on Java).
- Boss death animations longer than Bedrock's 20 ticks keep counting after the engine removed the
  actor (the chest appears at TF's time), but the dying body is gone after 20 ticks; units that
  need a longer visible death keep the boss alive through `Behaviour::hurt` / `gf::death`.

## Fallback and follow-ups

- If `Actor::tick` stops being called for some actor class after an update, the dispatch moves to
  the level tick over `Level::getRuntimeActorList()` (same per-actor code).
- Exact RGB: draw TF's bar through F12's `hud::addLayer` (ClientTFBossBar#renderBossBar: the white
  bar textures tinted with the RGB) once F12 lands, or find the real offset of
  `ClientInstanceScreenModel::mBossInfo` (BeDD / a debugger) and drop the guard; vanilla clients are
  unaffected either way.
- F2: run the converter on the Hydra, Naga and Snow Queen and check their part geometry with the
  `<id>_part` + `<ns>:part` convention above (the open half of this spike).
- Deviations recorded in the PR: parts of a parent without its own part type use
  `gloamingforest:part`; the sinister spawner block entity is not part of this kit (U22).

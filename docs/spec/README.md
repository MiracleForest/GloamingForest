# GloamingForest specification index

GloamingForest reproduces the upstream Java source pinned in NOTICE (version 4.8, branch `1.21.1`, commit
`9e40a75721c716b2fdf80c16d1058fe718825e9f`) on Bedrock 1.26.51 / LeviLamina 26.51.7. The work is split into waves of
units; each unit owns disjoint ids and paths and integrates with the others only through the W0 contracts (see
[AGENTS.md](../../AGENTS.md), rules R1-R25).

| File | What |
|---|---|
| [units.json](units.json) | The plan's records verbatim: waves, units (paths, content, contracts, e2e), rules, contracts, deviations, risks, build throttle. |
| [owners.tsv](owners.tsv) | The owner of every id of every kind and of every path (generated by `tools/spec/owners.ps1`). |
| [config.md](config.md) | Every upstream config key mapped to one unit config section. |
| [e2e.md](e2e.md) | The e2e recipe and scenario conventions. |
| [worker.md](worker.md) | How a unit worker works (the worker template). |
| `<unit>.md` | Behaviour spec of a unit (written by F14-F16), `blockstates.md` / `import.md` (F1), `models.md` (F2), `not-ported.md` (F16). |
| [../spikes/TEMPLATE.md](../spikes/TEMPLATE.md) | Template of the spike reports S1-S7. |

## owners.tsv

Columns: `kind`, `id-or-glob`, `owner`, `mode` (`gen`: produced by a tool, regenerate with `-Unit <unit>`; `manual`).
Ids carry their namespace (`gloamingforest:naga_stone`); tags are `<registry>/#<ns>:<path>`, registry entries
`<registry>/<ns>:<path>`; `path` rows are globs (`**` any path, `*` one segment, `{a,b}` alternatives; the most
specific match wins, an exact path beats any glob). `stub` rows are the placeholders F0 created in W0b directories;
`subcommand` rows are literal paths below `/gloamingforest` (see Subcommands).
`tools/ci/ownership.ps1 -Unit <unit>` checks a change against the `path` rows (against `origin/main` by default, so a
stale local `main` in a worktree does not count other units' merged work); assemble checks that every asset file
has an owner. The generated layers `assets/gen/{import,geo,audio}/<unit>/**` (mode `gen`) belong to their unit, and
their tool unit (F1 import, F2 geo, F3 audio) may also write them: the tools generate every unit's layer (R3).

### Per-unit files

Every W1 unit, and every W0b unit with `"unitFiles": true` in `tools/spec/owners.rules.json` (F1-F13), owns these
files by its unit name `<n>` (R3): `**/*.d/<n>.json` (pack fragments, tag unions), `assets/pack/rp/texts.d/*/<n>.lang`,
`assets/data/*/<n>.json`, `assets/lang/*/<n>.json` (its `tr` strings, R9), `assets/tags/**/*.d/<n>.json` (R6),
`tools/import/overrides/<n>.json` and `tools/sounds/recipes/<n>.json` (its sound refinements, R10). F8's are named
`entity`, F10's `combat`, F12's `ui`, F11's `families` (for example `assets/lang/en_us/families.json`).

### Pack folders

Plain (non-fragment) pack files live in a per-unit folder below their Bedrock pack directory:
`assets/pack/{bp,rp}/<pack dir>/<n>/**` is copied to `<pack dir>/<n>/**` of the assembled pack (for example
`assets/pack/rp/particles/landmark/protection.json` -> `particles/landmark/protection.json`). Every W1 unit owns
`assets/pack/{bp,rp}/**/<n>/**`; of the W0 units F4 (`dimension`), F6 (`landmark`), F8 (`entity`, `boss`), F10
(`combat`) and F12 (`ui`). F10 also owns `assets/pack/rp/particles/fx/**` (only there: a bare `fx` unit folder would
take `fx` folders inside other units' folders, such as F12's `textures/ui/fx`) for its own particle effects (the `fx`
contract: Java's portal colour and coloured
`DustParticleOptions` motion, which no vanilla Bedrock effect reproduces): `assets/pack/rp/particles/fx/<name>.json`
-> `particles/fx/<name>.json`. Folders ending in `.d` are fragment directories: they are merged by a
`tools/xmake/merges.json` entry and never copied, so a `.d` folder without a merge entry ships nothing. A unit
folder nested in another unit's folder belongs to the inner one: the unit-folder rules (`<prefix>/**/<folder>/**`)
that match a path compete as one group with the score of their best member, and inside the group the folder nearest
the file wins (`assets/pack/rp/textures/biomes/combat/x.png` is F10's, `assets/pack/rp/entity/hydra/x.json` is
U24's). A more specific rule that is not a unit-folder rule, such as `assets/pack/rp/particles/fx/**`, still beats
the group; other rules tied in specificity with different owners fail as ambiguous. A particle effect's `particle_effect.description.identifier`, like a block's, item's or
entity's identifier, may appear once per layer; a manual file with a generated file's identifier replaces it. The
assemble check `checks.packPathProbes` (merges.json) builds a probe file in each granted folder (F10's
`particles/fx` and `particles/combat`, one folder of F6, F8 and a W1 unit, three nested unit folders, among them `entity/hydra`) into a
scratch pack and fails unless it reaches the same path below the pack (`assets/pack/<bp|rp>/<p>` -> `<p>`) and
`owners.tsv` gives it to that unit; `tools/assemble.ps1 -Check` also runs `tools/ci/ownership.ps1 -PackProbes`, which
holds the CI ownership gate to the same expectations.

### Assemble: merges and the reference check

`tools/xmake/merges.json` merges fragment directories (`*.d/<unit>.json`) of the gen layer and then the manual layer
(the manual layer wins per id; a duplicate inside one layer fails; a plain file at a merge's output path fails, since
the merge would overwrite it). Besides the atlases, `sound_definitions`, music,
`blocks.json`, texts and the item catalog, `rp/sounds.json.d/<unit>.json` -> the resource pack's `sounds.json` (mode
`categories`): the ids of `block_sounds`, `entity_sounds.entities`, `individual_event_sounds.events`,
`individual_named_sounds.sounds`, `interactive_sounds.block_sounds` and `interactive_sounds.entity_sounds.entities` are
merged one by one; any other key fails (vanilla's defaults stay). A block names its sound in `blocks.json` (`"sound": "<block_sounds id>"`). F11's family
generator runs after the merge: for every upstream sound type a block of the pack uses (`SOUND_TYPES` of
`tools/families/families.lua`, today only `gloamingforest.jar`) it writes the `gloamingforest.<type>` entries of
`block_sounds` and `interactive_sounds.block_sounds` into the merged `sounds.json`, replacing an entry of the same id.
Fragments may define `gloamingforest.<type>` ids like any other (F1's `rp/sounds.json.d/import-flora.json` defines
`gloamingforest.jar` with the same values), but while a block uses that sound type the generator's entry is the one
that ships; refine those volumes and pitches in the generator, not in a fragment.

The dangling-reference check resolves every `gloamingforest:` value of the BP and data files: against BP definitions,
data files by registry (`tags/worldgen/<registry>/` and `tags/gloaming/<registry>/` are two-segment tag registries),
owners.tsv and the reviewed ids of `tools/import/known-ids.json` (F1), each by its kind. The values of `tag`, `tags`
and `generates_on` (and the import's `tagValuedKeys`) name tags, with or without `#`, of the registry the context gives:
the `tag` of a recipe (Java data or Bedrock BP recipe) is an item tag, `generates_on` and the `tag` of a
`minecraft:matching_block_tag` predicate or `minecraft:tag_match` rule test a block tag, any other a tag of any
registry. Two `tags` lists are not references: an item's `minecraft:tags` component declares Bedrock item tags (they
count as known item tags, so a unit may give an item a Bedrock-only tag and use it in a BP recipe) and a Bedrock
recipe's `tags` name its crafting stations. A `gloamingDangling` reference of `known-ids.json` (dangling in upstream itself, kept
for parity) is a warning when its kind matches the reference (a `tag:<registry>` entry covers only a tag reference);
every other unresolved reference fails.

owners.tsv still spells the six `data/gloamingforest/tags/gloaming/wood_palettes/*` tags with a one-segment registry
(`gloaming/#gloamingforest:wood_palettes/<path>`, owner F9 by the fallback rule), the form F1's import looks them up
by. Moving them to the two-segment form (`gloaming/wood_palettes/#gloamingforest:<path>`) and to F7 is one joint change
of F0 and F1 (A8): `"tagRegistryGroups": ["worldgen", "gloaming"]` and a tag rule `gloaming/wood_palettes:*` -> F7 in
`tools/spec/owners.rules.json`, F1's `Data.cs` / `Known.cs` reading `tags/gloaming/` as two-segment, and the import
regenerated (the six files move from `assets/gen/import/item/` to `assets/gen/import/structure/`). Either half alone
fails `tools/import/run.ps1 -Check`.

## Deviations

- Sounds and music (229 upstream files for 328 events, 9 discs) are All Rights Reserved: every event is re-synthesized (F3 baseline, owners refine, U10 composes the 9 tracks and dimension music). They cannot be identical; A7 reviews quality.
- 274 structure templates (.nbt) are All Rights Reserved: lich tower 182, courtyard 32, camp 35, features 21, final castle 3, quest grove 1 are re-designed in the GloamingForest template format with upstream's footprint, slots/connectors (LGPL template definitions), rooms, spawners, chests and loot; procedural structures are exact translations.
- Compat not ported: JEI/REI/EMI (75 files), Jade/TOP, Curios charm rendering, CosmeticArmor, Museum Curator exhibits (66), the Tips mod (99 tips), OptifineWarningScreen, JappaPackReloadListener (Jappa textures toggle), ModUpdateURLInterceptor. Workaround: tooltips and in-game screens; tips may later become loading tips.
- Structure keys quest_island, druid_grove, floating_ruins and world_tree have no implementation in upstream 4.8 and Boggard is commented out: not ported.
- Locales: upstream ships 99 lang files; Bedrock supports 29 locales, so the rest (including en_ud) are dropped.
- No new enchantment or effect ids for vanilla clients (Enchant::Type has 42 fixed, MobEffect 38): fire_react, chill_aura, destruction, renewal live in item user data with server-written lore and glint; frosted uses a hidden Slowness carrier. The client mod shows exact tooltips and HUD icons.
- Custom dimension height (-32..256) and fixed time 13000 rely on S1; vanilla clients get per-player SetTimePacket and doDaylightCycle packets. If the native definition fails for vanilla clients, they may render below y 0 incorrectly.
- Sky, aurora and weather shaders: there is no GLSL in RenderDragon, so they become CPU meshes with built-in materials (client mod). Vanilla clients get client-biome sky and fog colours and PlayerFogPacket only.
- Client-authoritative movement (12 Travellers' Gear movement modifiers, yeti throw, custom knockback) is exact only with the client mod. Vanilla clients get approximations: motion packets on input edges, Slow Falling for glide, and no step-up or water walk.
- Climbable custom blocks (climbable hollow logs and similar) can be climbed only with the client mod. On vanilla they are not climbable.
- Custom screens (uncrafting table, advancement tree, item displays) fall back to DDUI, forms or a JSON-UI container skin on vanilla. The Java advancement frame textures are Mojang's (All Rights Reserved) and are redrawn.
- Boss bars use exact RGB with the client mod and the nearest of 8 BossBarColor values on vanilla. The 15 upstream map decorations are mapped to the 30 vanilla MapDecoration types on vanilla.
- Giants render with the viewer's skin (giantSkinUUIDs) only with the client mod. Vanilla clients see the default skin.
- Banner patterns, trim materials and record items for vanilla clients depend on spike S6. If unknown ids crash a vanilla client, the server strips them for vanilla clients. If RecordItemComponent cannot take custom sounds, discs play through a jukebox hook and PlaySoundPacket, keeping comparator output.
- Block entities depend on spike S3. If data-driven block actors are not usable, signs, chests, casket, drying racks, jars and candles use BlockData plus display entities or container entities, and vanilla clients see static geometry.
- Creative tabs become Bedrock creative catalog groups (there are no top-level tabs). Durability and dose bar colours, the title splash and the Halloween visuals are client-mod only.
- NeoForge config files and screen become per-unit JSON plus /gloamingforest config. The Skylight world type becomes a config option, because Bedrock has no world-preset choice for custom dimensions. Java data-pack overrides of upstream registries are baked into the packs.
- The mod_exists loot condition only recognises gloamingforest and minecraft. PlateauBoss stays a placeholder, as in upstream.
- Keybinds get keyboard defaults only. Touch and controller players use item-use fallbacks.

## Risks

- S1 custom dimension for vanilla clients (height, chunk sync, map dimension id). Mitigation: F4 runs the spike first and tries both the native DimensionDefinition and the vendored MoreDimensions route; the remote-vanilla e2e gates W1.
- Worldgen parity, determinism and speed on worker threads, cross-chunk trees and terraforming before noise. Mitigation: Java-parity core with gtests, F13 oracle goldens, LargeWriter, per-chunk timing budget in U2 and A1.
- RenderDragon hooks (sky, world render, tint, HUD) are fragile and differ under Vibrant Visuals. Mitigation: one F12 client contract, spike S5, screenshot goldens in both modes; units never hook rendering directly.
- Client-authoritative movement: rubber-banding or anti-cheat kicks for double jump, glide and yeti throw. Mitigation: U12 is isolated, has server validation, and has a vanilla fallback path.
- Custom block entities (S3) are uncertain and affect chests, signs, casket, drying racks, jars, candles and spawners. Mitigation: backend-neutral inventory and families contracts, with a BlockData + entity fallback.
- Content volume: 533 blocks and 80 entities mean long pack load times, Bedrock block permutation limits and client memory. Mitigation: a permutation budget check in assemble, and integer states declared as lists.
- Volume and fidelity of the ARR template re-designs (274), and agents accidentally deriving from upstream .nbt. Mitigation: the sparse checkout excludes them, CI hash guard, the DSL plus validator against the LGPL template definitions, and golden screenshots.
- Model converter fidelity and Molang animation limits (about 32 actor properties): multipart bosses (Hydra up to 7 heads, Naga segments, Snow Queen shields) built as linked actors can desync. Mitigation: spike S4 on the hardest models, seeded boss selftests, a multiplayer soak in A8.
- W0 contract gaps found mid-W1. Mitigation: the src/feature/ext/<u>/ escape hatch, coordinator triage, A8 folding.
- Hidden coupling through tags, data maps, sound events and shared loot tables. Mitigation: owners.tsv covers every kind, the ownership CI check, the dangling-reference check, and union-only tag fragments.
- Machine contention: 47 GB RAM, 20 CPUs, 5 BDS and 2 client e2e slots for up to 16 agents. Mitigation: Throttle slots with a memory gate, two W1 batches, server-only iteration builds.
- Symbols missing or different between the server and client header sets (MCNAPI, client-only classes). Mitigation: check headers before use, every spike compiles both targets, CI matrix.
- Licensing: the CC BY-NC-SA ShareAlike and NonCommercial terms apply to the released packs, and no All Rights Reserved file may ever land in the repo. Mitigation: NOTICE/assets/LICENSE in W0a, the A7 licence audit, arr-guard.
- GitHub API rate limits (hit during this review) would stall agents that read upstream online. Mitigation: the shared local checkout via tools/upstream/fetch.ps1.
- Synthesized audio and music quality may feel far from upstream. Mitigation: per-event recipes owned by feature units and an A7 review loop.
- Vanilla clients crashing on unknown ids (banner patterns, map decorations, entity properties, custom items in packets). Mitigation: spike S6, a per-unit remote-vanilla e2e, the A7 matrix.

## Build throttle

Implement tools/lib/Throttle.psm1 in W0a: Enter-GfSlot -Pool build|bds|client takes a lock file %LOCALAPPDATA%/gf-throttle/<pool>/<n>.lock opened with FileShare.None, so the OS releases it if the process crashes. The holder writes its PID, worktree and unit for diagnostics, and waiters poll every 10 s. tools/build.ps1 and tools/e2e/*/run.ps1 are the only entry points (rule R23).

Build pool: 3 slots, each running xmake -j6 (18 compile jobs on 20 CPUs). A slot is granted only when at least 10 GB of physical memory is free. '-Target all' builds server then client inside one slot, and gtest runs in the slot. A separate mutex guards 'xmake require' and the shared package cache. Precompile the mc/ and ll/ headers per target type, and evaluate a shared xmake build cache so fresh worktrees do not start cold.

BDS pool: 5 slots, reusing Levitate's lv-e2e slot directory so both projects share it, with server max-threads=2. Client pool: 2 BeDD slots on the same bei-e2e.lock / hiN-e2e.lock files as Levitate.

Memory budget: about 27 GB for builds, 7 GB for BDS, 7 GB for clients and 6 GB for agents, roughly 47 GB in total. That is why builds have a memory gate.

Agent discipline: iterate with '-Target server' and the unit's selftest glob. Build the client only when client code changed. Run '-Target all -Tests' plus the unit's server, client and remote-vanilla scenarios once before opening the PR. At merge, the coordinator runs the 'full' selftest scenario and the client smoke test.

Concurrency: at most 16 agents. W0a uses 1 agent; W0b's 16 units run as one batch. W1 runs in two batches of 15. Batch 1 holds the highest-risk and most-referenced units: U1, U2, U3, U4, U5, U11, U12, U13, U14, U15, U20, U21, U24, U26, U28. Batch 2 holds the rest. W2a runs 7 audits in parallel, then A8 alone, repeated until a round is clean.

CI (GitHub Actions): server/client matrix, gtest, 'assemble -Check', import/synth/template '-Check', ownership and arr-guard. E2E runs only locally on the coordinator.

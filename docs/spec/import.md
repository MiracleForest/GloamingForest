# Import tool and content skeleton (F1)

`tools/import/run.ps1` (contract "import") turns The Twilight Forest 4.8 (`9e40a757`) from the shared local
checkout (`tools/tf/fetch.ps1`, rule R24) into the generated layer `assets/gen/import/<unit>/**`, partitioned by
[owners.tsv](owners.tsv) (rule R3). Units never edit that tree: they regenerate it (`-Unit <unit>`), change it
through `tools/import/overrides/<unit>.json`, or override a file with a manual one of the same id under
`assets/pack/**`, `assets/lang/**` or `assets/data/**` (the manual layer wins per path, per BP identifier and per
fragment key, see `tools/xmake/assemble.lua`).

```powershell
pwsh tools/import/run.ps1                                   # everything (about 3 s after the first compile)
pwsh tools/import/run.ps1 -Kinds textures,models -Unit trees
pwsh tools/import/run.ps1 -Check                            # CI: the committed tree is reproduced byte for byte
```

The importer is C# (`tools/import/src/*.cs`), compiled by `run.ps1` with `Add-Type` and cached per source hash in
`%TEMP%\gf-import`. It never opens TF's `.ogg` or `.nbt` files (rule R10; the checkout does not contain them).

## References

Every `twilightforest:` string of the generated data and BP files must name something that exists. The import
resolves each one (`Known.cs`) against the generated data files (tags with Java's registry paths, including the
two-segment `tags/worldgen/<r>/` and `tags/twilight/<r>/`), the BP definitions, owners.tsv and the reviewed
allowlist **`tools/import/known-ids.json`**: every id TF registers in code (travellers modifier types, biome layer
types, template marker handler types, enforcements, the `pinch` damage effect, the dimension renderer, the
`twilight_biomes` biome source, attribute modifier ids), texture locations and the `camp/rack` template pool, each
with its kind, the reason and the TF source that registers it, plus the JSON keys whose values are tags written
without `#` (`tag`, `tags`, `generates_on`). A reference found nowhere **fails the import**. References that are
dangling in TF itself are listed under `tfDangling` and reported as a warning on every run: only
`twilightforest:equipment/travellers_chest` (the `craft_vest` criterion of advancement `craft_travellers_gear` names
the recipe's pre-rename id; TF renamed it `travellers_vest` and the criterion never triggers in TF either; kept
verbatim for parity). An allowlist entry no data references any more is reported as stale.

assemble's dangling-reference check (`tools/xmake/assemble.lua`, F0) does the same on the assembled packs
([issue #21](https://github.com/MiracleForest/GloamingForest/issues/21), fixed in F0's W0c): it reads
`tools/import/known-ids.json` itself (its `ids` known by kind, its `tfDangling` references reported as warnings),
types the values of tag-valued keys as tags and reads `tags/twilight/<registry>/` as a two-segment registry. The
import therefore writes no index file for it (the W0b bridge `data/twilightforest/gf_known/**` is gone); it keeps its
own check so that a dangling reference fails at generation, next to the TF file that names it. `assemble -Check`
reports the one `tfDangling` reference as its only warning.

## Sound events

F3 (`tools/sounds/synth.ps1`) writes the resource pack's `sound_definitions` for all 328 TF sound events, one
fragment per owner (`assets/gen/audio/<u>/rp/sounds.d/<u>.json`), from its synthesized audio. assemble merges every
`rp/sounds.d/*.json` of the generated layers into one object and fails on a key defined twice, so the import emits
**no** `sounds.d` fragment and no sound files: TF's `.ogg` files are All Rights Reserved and never opened (rule R10).
The `sounds` kind only checks TF's `sounds.json` against owners.tsv (every event must have an owner) and leaves a
data listing per owner (`data/gf/sound_events/<unit>.json`) that F3 and the owners may read: Bedrock category,
subtitle key, and TF's sound names (which variants an event has, vanilla events it reuses). The subtitle keys are
imported with the rest of the lang (`subtitles.twilightforest.*`, owned by the event's owner).
## Owners

Every file goes to the owner of its id (owners.tsv kind): blocks, block items, items, spawn eggs, entities, lang
keys, loot tables, recipes, advancements, tags, worldgen ids, registry entries, data maps, particles, sound events.
Shared files get one owner by rule:

- a **texture** belongs to the unit whose blocks / items / entities / particles use it, F1 when several units use
  it; unused textures follow the block, item or entity of their file name (`entity/<id>/...`), else F1;
- a **block geometry** belongs to the unit of the blocks using it, F1 when several units share it (the vanilla
  parent shapes: stairs, slabs, fences, ...);
- ids without an owner row (minecraft-namespace worldgen, NeoForge's loot modifier list) go to F1.

## Blocks

- States: see [blockstates.md](blockstates.md) (frozen, rule R1). The properties are those the block's Java class
  chain declares (`JavaStates.cs`): every `createBlockStateDefinition` override of the TF classes
  (`builder.add(...)`, chained `.add(...)`, `LIST.forEach(builder::add)`, following `super` calls), then the full
  property set of the vanilla class reached (Minecraft 1.21.1: `TrappedChestBlock`, `MultifaceBlock`,
  `ChiseledBookShelfBlock`, ...); constants are resolved through the class, its TF superclasses and interfaces
  (`LightableBlock.LIGHTING`, `SnowLoggable.SNOW_LAYERS`), its static imports and the vanilla constants, to their
  `Property.create` name, integer range or enum values (serialized names in declaration order). Java property `p`
  -> `twilightforest:p`, same values; integer lists start at 0; `waterlogged` is dropped (Bedrock's liquid layer);
  no placement traits. The first listed value is the Bedrock default: an enum and a boolean list TF's default first
  (`registerDefaultState`, through local `BlockState` variables and `for` loops; `StateDefinition.any()` for what it
  does not set, which makes an unset boolean `true`: trophies `powered`, `HugeMushroomBlock` faces, rope `y`,
  terrorcotta `rotated`, `locked`), so a boolean is `[true, false]` where TF's default is `true` (the selftest
  `import.bool_defaults` checks in game that Bedrock 1.26.51 honours that order: the default permutation has the
  state `true`, and a permutation condition on it follows the value). Integers keep Bedrock's `0` default (the list
  must start at 0); blockstates.md lists TF's default where it differs (leaves `distance=7`, candles `candles=1`, ...).
- Checks (every run, `-Check` included; a failure fails the run): the Java properties of every block against a
  hand-written golden, `tools/import/expected-states.json` (one entry per TF block class, read by hand from the
  Java sources); the states of every generated BP block file (after the overrides) against the same golden; every
  blockstate property and value TF's blockstate file uses must be a Java property value; the rotation of every
  variant, evaluated as Bedrock does (root components, then the matching permutations in order), against TF's
  blockstate file (3659 variants; a condition on a state the file does not declare, for example after an override
  renamed it, is an error); the behaviour values of 77 blocks (every drying rack, the brazier, the berry and oreberry
  bushes, the unbreakable and per-state ones, a block of every tool, tier and drop rule, a sample of the rest)
  against a second hand-written golden, `tools/import/expected-behaviour.json` (hardness, explosion resistance in
  Java units and map colour per state, sound, tool and tier tags, `requiresCorrectToolForDrops`).
- Variants: a permutation per variant key (Molang `q.block_state(...)` conditions), its model's geometry and
  material instances, and `minecraft:transformation` rotation `[-x, -y, 0]` for Java's `x` / `y` (Java rotates
  clockwise seen from above / the axis; Bedrock follows the right-hand rule). The default state's variant is also
  the root visual. A permutation replaces only the components it names, so every permutation of a block with a
  rotated variant states its rotation, `[0, 0, 0]` included (an upright `aurora_pillar` must not inherit the
  lying one's). Weighted random variants use their first model. `uvlock` is not supported by Bedrock.
- Multipart (fences, walls, panes, ...): one geometry per block, a bone per part rotated about the block centre (bone
  rotation `[x, y, 0]`),
  visibility from the part's `when` condition (a part without one is always shown).
- Geometry: Java elements `from`/`to` (0..16) become Bedrock cubes with `origin = [8 - to.x, from.y, from.z - 8]`
  (Bedrock's model x axis is mirrored), per-face UVs (up / down faces flipped as Bedrock maps them), face
  `rotation` -> `uv_rotation`, element rotation -> cube `pivot` / `rotation` `[-x, -y, z]` (`rescale` applied to the size),
  clamped to Bedrock's 30x30x30 limit. A single full cube with default UVs uses `minecraft:geometry.full_block`.
  Models without elements (block entity renderers, custom loaders) render as a cube with their particle
  texture until the owner adds its renderer.
- Render method: `translucent` -> `blend`, `cutout(_mipped)` -> `alpha_test`, otherwise `alpha_test` when a face
  texture has transparent pixels, else `opaque`.
- Behaviour values: `seconds_to_destroy` = Java hardness (`false` when unbreakable), `explosion_resistance` =
  Java resistance **x 5** (`false` from 3600000: giant obsidian, `Float.MAX_VALUE`): the game stores a fifth of a
  JSON block's `explosion_resistance` (measured on 1.26.51: 3 -> 0.6, 50 -> 10, 6000 -> 1200) and its vanilla blocks
  at Java's values (stone 6, oak planks 3, obsidian 1200, bedrock 3600000), so the factor makes a TF block resist
  as the vanilla block of the same Java resistance (`import.behaviour` calibrates on the vanilla blocks:
  `twilight_oak_planks` holds what `minecraft:oak_planks` holds, `underbrick` what `minecraft:stone` holds; the
  hardness needs no factor). They follow `BlockBehaviour.Properties`:
  `of()` starts at destroyTime 0 / explosionResistance 0 / `SoundType.STONE` (the brazier, which sets no strength,
  breaks at once); the calls apply in order, `strength(f)` sets both, `destroyTime` and `explosionResistance` only
  their own (the berry bushes' `destroyTime(0.4F)` keeps resistance 0), `explosionResistance` keeps `max(0, r)`,
  `instabreak()` = `strength(0)` (a block is instabreak when its final values are 0, whatever call set them);
  arguments are literals or products of literals (`strength(0.2F * 64.0F, 15.0F)`).
  Java's explosions do not look at the hardness, so an unbreakable block with a low resistance still explodes
  (`twilight_portal`: `strength(-1.0F)`, resistance 0, as the nether portal). Copies: `ofFullCopy` /
  `ofLegacyCopy(X)` and `copyAndScaleProperties(X, k)` (the drying racks: a copy of the slab, destroyTime and
  explosionResistance x `k`); a vanilla `X` uses Minecraft 1.21.1's values (glass, slime block with its friction,
  leaves, planks, wooden slabs, wood / hyphae with each wood's map colour and sound, ...); every property of a copied
  TF block is copied (light function, friction, collision, occlusion, `requiresCorrectToolForDrops`; the vanilla
  stone, cobblestone, stone bricks, obsidian and spawner require it). Registration helpers are read with their
  arguments (`ominousCandle(name, MapColor.SAND, ...)`), and calls a TF class chains onto the properties in its
  constructor (`SpecialMagicLogBlock`) apply after the registration's; a block is resolved completely (its copy, then
  its class's calls) before another block copies it, as Java's `ofFullCopy` reads the Properties the source's
  constructor already changed. A block whose properties come from a helper the import does not read, or a copy it
  cannot resolve, is a warning. State-dependent values become permutations
  (the default state's value on the root): `getExplosionResistance` overrides (vanishing blocks: 6000 while
  inactive, a locked vanishing block 6000000, skull chest and keepsake casket `Float.MAX_VALUE`), the trophy
  pedestal's `getDestroyProgress` (unbreakable while inactive), the map colour of `logProperties(top, side)` (the
  side colour on a lying log) and of the castle doors (their colour; `MapColor.NONE` while vanished, which lets
  Java's map look through the block, has no Bedrock equivalent). Overrides that depend on the player or the held
  item (shears on arctic fur and berry bushes, the aurora brick's advancement, the stronghold shield's side) are
  the owners' runtime behaviour and listed in the import log. A `getDestroyProgress` override returns progress per
  tick, not a hardness: only `-1` (cannot be mined in that state) and `super` are block values; any other constant
  is reported (a warning) and left to the owner. `MapColor` RGB (`DyeColor` through its map colour);
  `friction` = 1 - Java friction; no collision for `noCollission`; the Java sound type -> the Bedrock block sound
  (an unmapped one warns). Bedrock's `blocks.json` names a block sound *type* of the engine (or of a pack's
  `sounds.json` `block_sounds`), not sound events, so the closest one stands in where the Java type has none:
  `LILY_PAD` -> `grass` (Bedrock's own `waterlily` uses `grass`, vanilla `blocks.json` 1.26.51; Java's lily pad
  differs only in its place sound), `FLOWERING_AZALEA` -> `azalea` (the vanilla `blocks.json` names no flowering
  azalea type; the three troll roots use it). TF's own sound types (`TFSoundTypes.java`: `JAR`, NeoForge's
  `DeferredSoundType(volume, pitch, break, step, place, hit, fall)` of `TFSounds` events) become sound types of the
  pack: `twilightforest.<type>` (`twilightforest.jar`: the mason jar, firefly jar, firefly particle spawner and cicada
  jar), written to `rp/sounds.json.d/import-<owner>.json` (assemble merges it into the resource pack's `sounds.json`
  per id; one file per owner of the blocks using the type, F1 when several units do): `block_sounds` break, place
  and hit, `interactive_sounds.block_sounds` step and fall, each with F3's event (`block.twilightforest.jar.*`) at the
  volume and pitch Java plays it for a type of volume v and pitch p (break and place (v + 1) / 2 at p x 0.8, hit
  (v + 1) / 8 at p x 0.5, step v x 0.15 at p, fall v x 0.5 at p x 0.75); Bedrock's jump and land, which Java has no
  sound of their own for, play the step and the fall. F11's family generator writes the same entries after the
  merge (`tools/families/families.lua` `SOUND_TYPES`), identical, so the result does not depend on the order. Flammability: only the 180 blocks TF registers with
  `FireBlock.setFlammable(block, encouragement, flammability)` (`RegistrationEvents.java`) get
  `minecraft:flammable` (`catch_chance_modifier` = encouragement, `destroy_chance_modifier` = flammability);
  `ignitedByLava` alone does not make a block burn in Java. Blocks not listed in a creative tab get
  `menu_category: none`.
- Tools and drops (`Harvest.cs`): Minecraft 1.21.1's tools mine a block faster when it is in their tag
  (`DiggerItem`: `#minecraft:mineable/<pickaxe|axe|shovel|hoe>` at the tier's speed; `SwordItem`: cobwebs at 15,
  `#minecraft:sword_efficient` at 1.5; `ShearsItem`: `#minecraft:leaves` at 15, `#minecraft:wool` at 5), and drop a
  `requiresCorrectToolForDrops()` block only when the tool is correct for it (in its mineable tag and not in its
  tier's `#minecraft:incorrect_for_<tier>_tool`, i.e. not in a `#minecraft:needs_<higher tier>_tool`). The import
  resolves TF's tag JSONs together with the vanilla 1.21.1 tags they reach (`#minecraft:mineable/axe` includes
  `#minecraft:planks`, `#minecraft:logs`, `#minecraft:signs`, `#minecraft:wooden_slabs`, ...; `Data.BaseBlockTagRefs`)
  and gives every TF block the Bedrock block tags the game gives its own blocks (measured on 1.26.51: stone
  `minecraft:is_pickaxe_item_destructible`; iron ore also `minecraft:stone_tier_destructible`, diamond block
  `minecraft:iron_tier_destructible`, obsidian `minecraft:diamond_tier_destructible`; oak leaves `minecraft:leaves` +
  `minecraft:is_hoe_item_destructible`; cobweb `minecraft:is_shears_item_destructible` +
  `minecraft:is_sword_item_destructible`): `minecraft:is_{pickaxe,axe,shovel,hoe}_item_destructible` for the
  mineable tags, `minecraft:is_sword_item_destructible` for `#minecraft:sword_efficient`, `minecraft:leaves` and
  `minecraft:is_shears_item_destructible` for `#minecraft:leaves`, `minecraft:is_shears_item_destructible` for
  `#minecraft:wool`, and, for a block a tool mines, `minecraft:{stone,iron,diamond}_tier_destructible` for
  `#minecraft:needs_<tier>_tool` (`aurora_block` is in `needs_diamond_tool` but no mineable tag: no tier tag, as the
  tier changes nothing in Java). With these, the vanilla pickaxes, axes, shovels and hoes mine and harvest a TF
  block exactly as the vanilla block of the same Java values (measured, `import.harvest_mining`). Bedrock's vanilla
  shears and swords single out their own leaves and cobwebs by block type, not by a tag a JSON block can carry:
  on TF's leaves the vanilla shears mine at 5 (the speed they give `minecraft:is_shears_item_destructible`; Java
  15) and a vanilla sword at 1 (Java 1.5) - a gap of the engine, left to the leaves' owner (U3) and the sword
  owners, who can correct it at run time through F9's item contract.
  A JSON block cannot declare Java's `requiresCorrectToolForDrops` (vanilla blocks carry it in their vanilla
  block data), so the import lists those blocks in `data/gf/import/harvest.json` and the runtime
  (`src/feature/ext/import/Harvest.cpp`, extension of this contract) sets the engine's flag on their block types
  when a world is ready and, on a client, when a GloamingForest server accepts the companion handshake: the game
  then drops such a block only for a tool that harvests it and mines it at its slower no-harvest speed otherwise,
  exactly as vanilla stone and obsidian (`import.harvest_tags`, `import.harvest_mining`, `import.harvest_drops`
  measure this against vanilla blocks and tools). The block's own loot (F10's `gf::loot` for TF's loot tables) is
  rolled by the owner only for a harvest the game allowed; a vanilla client on a BDS host does not have the flag
  on its own block types (its mining prediction for such a block is the faster one; the server decides the drop).
- Tools (`Skeleton.cs`, `Harvest.Digger`): every tiered TF tool (`TieredItem` subclasses by class chain:
  `PickaxeItem`, `AxeItem`, `ShovelItem`, `HoeItem`, `SwordItem`, whatever the TF class is called) gets Bedrock's
  item tags `minecraft:is_<kind>` (+ `minecraft:is_tool` for diggers) and the tier whose blocks it drops
  (`minecraft:{wooden,stone,iron,diamond,golden,netherite}_tier`, from the vanilla `incorrect_for_<tier>_tool` its
  `TFToolMaterials` tag includes: ironwood iron, steeleaf and knightmetal diamond, fiery netherite, giant stone, ice
  and glass wooden; `Tiers.X` for the minotaur axes, the mazebreaker and stale bread), and a `minecraft:digger`:
  a digger mines blocks with its kind's block tag at the tier's speed (`TFToolMaterials`: ironwood 6.5, steeleaf 8,
  knightmetal 8, fiery 9, giant 4), a sword cobwebs at 15 and `minecraft:is_sword_item_destructible` /
  `minecraft:leaves` blocks at 1.5, `use_efficiency` on (Java's efficiency). The game lets a custom item harvest
  every block its digger lists, whatever its tier tags (measured: an ironwood pickaxe with `minecraft:iron_tier`
  harvested obsidian), so a digger's condition leaves out the blocks of the tiers above the tool's
  (`!q.any_tag('minecraft:diamond_tier_destructible', 'minecraft:netherite_tier_destructible')` for an iron tool;
  the legacy `<tier>_pick_diggable` tags of vanilla blocks list the pickaxes that can dig them, no requirement, and
  are not read): those blocks drop nothing for the tool, as in Java, but mine at speed 1 where Java keeps the
  tier's speed (a digger entry always harvests, so Bedrock cannot express speed without drop). Bedrock's digger
  speed is an integer (1.26.51 rejects 6.5 and 1.5 with "invalid numeric value"), so a fractional speed is rounded
  half up, the mining time closest to Java's (ironwood 7, the swords' 1.5 -> 2), and the 12 tools are listed in the
  import log for their owners (U7 / U8), who can give the exact speed through F9's `item::Behaviour::destroySpeed`.
  TF classes that change the speed by block (`GiantPickItem` x64 on giant blocks, `MazebreakerPickItem` x16 on
  `#twilightforest:mazebreaker_accelerated`) are listed in the import log and stay their owners' runtime behaviour
  (U7 / U29, `item::Behaviour::destroySpeed`). Armour's `minecraft:wearable` and the attack damage are the owners'
  (U7 armory, F9's item contract).
- Light: a constant `lightLevel` is the block's `minecraft:light_emission`. A state-dependent one (`Light.cs`: a
  `lightLevel` lambda of `TFBlocks.java` or of a block class constructor, or a `getLightEmission` override, the
  leaf-most of the class chain) is evaluated for every combination of the states it reads (ternaries, `==` /
  `!=`, `*`, `switch` on an enum, `BrazierLight.getLight()`, the candelabra's candle count): the default state's
  light on the root, one permutation per other light level (fire jets, ghast trap, carminite reactor and builder,
  vanishing blocks, magic log cores, torchberry plant, brazier, ominous candles, skull candles, candelabra,
  casket and skull chest with lava). The mason jar's light comes from its block entity's item and stays the
  owner's.
- Block format (`Blocks.BlockFormat`, `FamilyBlockFormat`; measured on BDS 1.26.51, [S7](../spikes/S7.md)): from
  format 1.26.20 a block file is read by the schema `SharedTypes::v1_26_20::BlockDefinition`, which keeps block tags
  in the component `minecraft:tags`, an **array** of tag ids (`"minecraft:tags": ["minecraft:is_pickaxe_item_destructible"]`;
  the item form `{"tags": [...]}` is refused, "expected an array"), refuses the older `"tag:<id>": {}` components
  ("not present in the Schema": the block does not load) and takes `minecraft:block_entity`; formats up to 1.26.10
  take only `"tag:<id>"` components (`minecraft:tags` is "not valid here") and refuse `minecraft:block_entity`. The
  import writes every block the game loads as written in **1.26.50** with the `minecraft:tags` array. The family
  blocks (the 347 of `data/gf/families`) are rewritten at assemble by F11's families kit, in its own format 1.26.0
  (`tools/families/families.lua` `FORMAT`), from a copy of the skeleton or from its `"tag:"` components: their
  skeleton is the kit's input, never loaded as written, and keeps 1.21.80 with `"tag:<id>"` components until the kit
  writes 1.26.20 or later (then `FamilyBlockFormat` becomes `BlockFormat`). For a family block the kit writes in
  1.26.50 (the chests, with `minecraft:block_entity` for F10's native container backend), the tags are the
  skeleton's `"tag:"` component names, as one `minecraft:tags` array. In the v1_26_20 schema a `bone_visibility`
  value is a Molang string (a boolean is refused): a multipart part without a `when` is not named (a bone
  `bone_visibility` does not name is shown).

## Items, entities, recipes

- Item icons: the Java item model's `layer0` (`item/generated`, `item/handheld`), else `textures/item/<id>.png`,
  else the model's particle texture. Stack size from `stacksTo`; durability from `durability`, from the tier of a
  tiered item (`TieredItem` and every subclass, whatever its name: `TFToolMaterials` or vanilla `Tiers` uses), from
  `ArmorItem.Type.getDurability(n)` (also through `TravellersArmorItem`'s `(type, properties, slots, durability)`
  constructor and a subclass's `super(...)`); a damageable item and every subclass of a vanilla single-stack class
  (tools, armour, bows, shields, ...) stacks to 1 (the class chain is walked, not the class name matched).
  `hand_equipped` for handheld models, the TF / `c:` / compat item tags the item is in (`minecraft:tags`;
  Java's `minecraft:*` tags carry engine meaning on Bedrock and are left to the owners, except the tiered tools'
  Bedrock tool tags and `minecraft:digger`, see *Tools* above), display name `item.twilightforest:<id>.name` (`tile....` for items that place their block).
- Spawn eggs are Bedrock's own (`<entity>_spawn_egg`, from the client entity's `spawn_egg` colours = TF's egg
  colours).
- Bedrock recipes: `crafting_shaped` / `crafting_shapeless` -> `recipe_shaped` / `recipe_shapeless` (tag
  `crafting_table`), `stonecutting` -> `recipe_shapeless` (tag `stonecutter`), `smelting` / `blasting` /
  `smoking` / `campfire_cooking` -> `recipe_furnace` (`furnace` / `blast_furnace` / `smoker` / `campfire` +
  `soul_campfire`), `smithing_transform` -> `recipe_smithing_transform`. `unlock` lists the items of the
  recipe's advancement (`inventory_changed`; an item tag such as `#c:ingots/ironwood` or `#twilightforest:arctic_fur`
  as its members, Minecraft 1.21.1's vanilla members included for `#minecraft:boats` / `#minecraft:saplings`, other
  mods' optional entries left out); an advancement without item criteria that unlocks on entering water (TF's 8
  boats) gets Bedrock's `PlayerInWater` context, as Bedrock's own boat recipes; only one with neither is
  `AlwaysUnlocked` (none at 9e40a757). Ingredients: Java item tags with a Bedrock
  equivalent (`minecraft:planks`, `logs`, `wool`, `wooden_slabs`) stay tags; tags of TF items only use the tag
  (declared on those items); other tags and ingredient lists are expanded into one recipe per combination
  (`<id>_<n>`); more than 64 combinations fail the import (a recipe is never cut down to some of its alternatives).
  Furnace and smithing recipes take one item per slot: every tag alternative (Bedrock-native ones included, with
  Minecraft 1.21.1's members of `minecraft:planks`, `wooden_slabs`, `wool`, `logs`) becomes its members, and a
  smithing recipe is emitted per template x base x addition combination. Their slots are plain item names, so an
  alternative with a data value (the water bottle) fails the import there instead of losing its data (none at
  9e40a757). NeoForge
  ingredients: `neoforge:difference` / `intersection` / `compound` become their item sets (the travellers belt's
  wooden chest that is not trapped), `neoforge:components` with a water potion becomes `minecraft:potion` data 0
  (tannin). A vanilla-type recipe that still has no Bedrock recipe is a warning and listed in the import log
  (none at 9e40a757).

## Families

`data/gf/families/<unit>.json` (F11 reads it; F11's contract names `assets/gen/import/<u>/data/families.json`, but
the gen layer's `data/` root is copied to the mod's `data/` with one file per path across every unit, so a fixed
name per unit collides: the import names the file after the unit under `data/gf/families/`, deviation). Each
entry: `family` is the shape family of the Java class chain (stairs, slab, fence, fence_gate, wall, door,
trapdoor, button, pressure_plate, pane, pillar, log, wood, leaves, sapling, potted, sign, hanging_sign, chest,
trapped_chest, horizontal, directional, climbable for `LadderBlock`), else the block's first trait family;
`params.traits` lists every trait family of the contract the block has, whatever its shape: `waterloggable` (a
`waterlogged` Java property), `snowloggable` (implements `SnowLoggable`), `climbable` (`LadderBlock`, or in
`#minecraft:climbable`), `lightable` (implements `LightableBlock`), `connected_texture` (a model with TF's
`connected_texture_block` loader).

## Lang

17 Bedrock locales have TF translations: en_US, cs_CZ, de_DE, el_GR, es_ES, es_MX, fr_FR, it_IT, ja_JP, ko_KR,
pl_PL, pt_BR, ru_RU, tr_TR, uk_UA, zh_CN, zh_TW. TF's bg_bg, da_dk, fi_fi, hu_hu, id_id, nb_no, nl_nl, sk_sk and
sv_se files are empty (`{}`) and TF has no en_gb, fr_ca or pt_pt file, so the other 12 Bedrock locales (en_GB,
fr_CA, pt_PT, nl_NL, bg_BG, da_DK, fi_FI, hu_HU, id_ID, nb_NO, sk_SK, sv_SE) get no import file: Bedrock falls
back to en_US for a key a locale's texts lack, and so does `gf::tr`. The 29 locales therefore show TF's texts, in
English where TF has no translation (as in Java).
## Chest boats

TF's `TextureGeneratorReloadListener` paints the vanilla oak chest boat's chest region into TF's chest boat
textures at runtime. The vanilla texture is Mojang's and cannot be redistributed, so the importer paints that
region (x 0..48, y 58..96 of the 128-wide texture, only when it is empty, as TF does) from TF's own twilight oak
chest texture: every face of the boat chest's boxes (lid 12x4x12, bottom 12x8x12, lock 2x2x1) is sampled from the
matching face of the chest model's boxes (14x5x14, 14x10x14, 2x4x1). The chest therefore looks like a twilight
oak chest instead of a vanilla oak one (deviation).

## Overrides

`tools/import/overrides/<unit>.json` (owned by the unit, applied on every regeneration, after generation and before
the files are written or checked):

```json
{
  "drop":   ["bp/blocks/some_block.json", "rp/textures/twilightforest/block/unused_*.png"],
  "patch":  {"bp/blocks/naga_stone.json": [{"op": "replace", "path": "/minecraft:block/components/minecraft:light_emission", "value": 15}]},
  "rename": {"rp/particles/x.json": "rp/particles/y.json"}
}
```

`drop` takes globs over the unit's generated paths, `patch` RFC 6902 operations `add` / `replace` / `remove` on a
generated JSON file, `rename` moves a generated file. A patch or rename target that is not generated fails the run.

## Determinism

The output depends only on the TF checkout, owners.tsv, owners.rules.json, merges.json, the overrides and the reviewed inputs `tools/import/known-ids.json`, `tools/import/expected-states.json` and `tools/import/expected-behaviour.json`. Text
inputs are read with line endings normalised to LF (the checkout may be CRLF on CI); JSON is written by an own
writer (order-preserving, 2-space indent, LF); generated PNGs are encoded by an own DEFLATE encoder (the
platform zlib differs between .NET versions); every collection is sorted ordinally. `-Check` compares every
generated file (and `docs/spec/blockstates.md`) with the committed one byte for byte and lists stale files.

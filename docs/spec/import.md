# Import tool and content skeleton (F1)

`tools/import/run.ps1` (contract "import") turns The Twilight Forest 4.8 (`9e40a757`) from the shared local
checkout (`tools/tf/fetch.ps1`, rule R24) into the generated layer `assets/gen/import/<unit>/**`, partitioned by
[owners.tsv](owners.tsv) (rule R3). Units never edit that tree: they regenerate it (`-Unit <unit>`), change it
through `tools/import/overrides/<unit>.json`, or override a file with a manual one of the same id under
`assets/pack/**`, `assets/lang/**` or `assets/data/**` (the manual layer wins per path, per BP identifier and per
fragment key, see `tools/xmake/assemble.lua`).

```powershell
pwsh tools/import/run.ps1                                   # everything (about 3 s after the first compile)
pwsh tools/import/run.ps1 -Kinds textures,models -Unit trees
pwsh tools/import/run.ps1 -Check                            # CI: the committed tree is reproduced byte for byte
```

The importer is C# (`tools/import/src/*.cs`), compiled by `run.ps1` with `Add-Type` and cached per source hash in
`%TEMP%\gf-import`. It never opens TF's `.ogg` or `.nbt` files (rule R10; the checkout does not contain them).

`data/twilightforest/gf_known/**` and `data/twilightforest/tags/gf_known/**` (F1) index the TF ids that TF's data
names but that are not data files (code-registered types such as travellers modifier and biome layer types,
marker handlers, restrictions, damage effects, texture locations, template ids, tags of TF's custom registries,
and Bedrock item tags). assemble's dangling-reference check only knows data files, BP definitions and owners.tsv
rows; the index makes it accept these ids. It has no runtime meaning.

## Owners

Every file goes to the owner of its id (owners.tsv kind): blocks, block items, items, spawn eggs, entities, lang
keys, loot tables, recipes, advancements, tags, worldgen ids, registry entries, data maps, particles, sound events.
Shared files get one owner by rule:

- a **texture** belongs to the unit whose blocks / items / entities / particles use it, F1 when several units use
  it; unused textures follow the block, item or entity of their file name (`entity/<id>/...`), else F1;
- a **block geometry** belongs to the unit of the blocks using it, F1 when several units share it (the vanilla
  parent shapes: stairs, slabs, fences, ...);
- ids without an owner row (minecraft-namespace worldgen, NeoForge's loot modifier list) go to F1.

## Blocks

- States: see [blockstates.md](blockstates.md) (frozen, rule R1). Java property `p` -> `twilightforest:p`, same
  values; integer lists start at 0; `waterlogged` is dropped (Bedrock's liquid layer); no placement traits.
- Variants: a permutation per variant key (Molang `q.block_state(...)` conditions), its model's geometry and
  material instances, and `minecraft:transformation` rotation `[-x, -y, 0]` for Java's `x` / `y` (Java rotates
  clockwise seen from above / the axis; Bedrock follows the right-hand rule). The first variant is also the root
  (default) visual. Weighted random variants use their first model. `uvlock` is not supported by Bedrock.
- Multipart (fences, walls, panes, ...): one geometry per block, a bone per part rotated about the block centre,
  visibility from the part's `when` condition.
- Geometry: Java elements `from`/`to` (0..16) become Bedrock cubes with `origin = [8 - to.x, from.y, from.z - 8]`
  (Bedrock's model x axis is mirrored), per-face UVs (up / down faces flipped as Bedrock maps them), face
  `rotation` -> `uv_rotation`, element rotation -> cube `pivot` / `rotation` (`rescale` applied to the size),
  clamped to Bedrock's 30x30x30 limit. A single full cube with default UVs uses `minecraft:geometry.full_block`.
  Models without elements (block entity renderers, custom loaders) render as a cube with their particle
  texture until the owner adds its renderer.
- Render method: `translucent` -> `blend`, `cutout(_mipped)` -> `alpha_test`, otherwise `alpha_test` when a face
  texture has transparent pixels, else `opaque`.
- Behaviour values: `seconds_to_destroy` = Java hardness (`false` when unbreakable), `explosion_resistance` =
  Java resistance, static `lightLevel`, `MapColor` RGB, `ignitedByLava` -> flammable, `friction` = 1 - Java
  friction, no collision for `noCollission`. Dynamic light levels (lit candles, fire jets, ...) are left to the
  owner. Blocks not listed in a creative tab get `menu_category: none`.

## Items, entities, recipes

- Item icons: the Java item model's `layer0` (`item/generated`, `item/handheld`), else `textures/item/<id>.png`,
  else the model's particle texture. Stack size from `stacksTo`, durability from `durability` (armor:
  `ArmorItem.Type.getDurability`), `hand_equipped` for handheld models, the TF / `c:` / compat item tags the item is in (`minecraft:tags`;
  `minecraft:*` tags carry engine meaning on Bedrock and are left to the owners), display name `item.twilightforest:<id>.name` (`tile....` for items that place their block).
- Spawn eggs are Bedrock's own (`<entity>_spawn_egg`, from the client entity's `spawn_egg` colours = TF's egg
  colours).
- Bedrock recipes: `crafting_shaped` / `crafting_shapeless` -> `recipe_shaped` / `recipe_shapeless` (tag
  `crafting_table`), `stonecutting` -> `recipe_shapeless` (tag `stonecutter`), `smelting` / `blasting` /
  `smoking` / `campfire_cooking` -> `recipe_furnace` (`furnace` / `blast_furnace` / `smoker` / `campfire` +
  `soul_campfire`), `smithing_transform` -> `recipe_smithing_transform`. `unlock` lists the items of the
  recipe's advancement (`inventory_changed`), else `AlwaysUnlocked`. Ingredients: Java item tags with a Bedrock
  equivalent (`minecraft:planks`, `logs`, `wool`, `wooden_slabs`) stay tags; tags of TF items only use the tag
  (declared on those items); other tags and ingredient lists are expanded into one recipe per combination
  (`<id>_<n>`, at most 64; beyond that the first alternatives: fiery armor's chestplate and leggings).

## Chest boats

TF's `TextureGeneratorReloadListener` paints the vanilla oak chest boat's chest region into TF's chest boat
textures at runtime. The vanilla texture is Mojang's and cannot be redistributed, so the importer paints that
region (x 0..48, y 58..96 of the 128-wide texture, only when it is empty, as TF does) from TF's own twilight oak
chest texture: every face of the boat chest's boxes (lid 12x4x12, bottom 12x8x12, lock 2x2x1) is sampled from the
matching face of the chest model's boxes (14x5x14, 14x10x14, 2x4x1). The chest therefore looks like a twilight
oak chest instead of a vanilla oak one (deviation).

## Overrides

`tools/import/overrides/<unit>.json` (owned by the unit, applied on every regeneration, after generation and before
the files are written or checked):

```json
{
  "drop":   ["bp/blocks/some_block.json", "rp/textures/twilightforest/block/unused_*.png"],
  "patch":  {"bp/blocks/naga_stone.json": [{"op": "replace", "path": "/minecraft:block/components/minecraft:light_emission", "value": 15}]},
  "rename": {"rp/particles/x.json": "rp/particles/y.json"}
}
```

`drop` takes globs over the unit's generated paths, `patch` RFC 6902 operations `add` / `replace` / `remove` on a
generated JSON file, `rename` moves a generated file. A patch or rename target that is not generated fails the run.

## Determinism

The output depends only on the TF checkout, owners.tsv, owners.rules.json, merges.json and the overrides. Text
inputs are read with line endings normalised to LF (the checkout may be CRLF on CI); JSON is written by an own
writer (order-preserving, 2-space indent, LF); generated PNGs are encoded by an own DEFLATE encoder (the
platform zlib differs between .NET versions); every collection is sorted ordinally. `-Check` compares every
generated file (and `docs/spec/blockstates.md`) with the committed one byte for byte and lists stale files.

# Block states (frozen)

Generated by `tools/import/run.ps1` (F1) from upstream 4.8 (`9e40a757`): the Bedrock block states of every upstream block. Rule R1: these
names and values are frozen; later units may only **add** states (or values), never rename or remove one.

Mapping rules (see [import.md](import.md)):

- The properties are upstream's own: every property the block's Java class chain declares in `createBlockStateDefinition`
  (`builder.add(...)` of each upstream class, following `super` calls, then the full property set of the vanilla class it
  extends) becomes the Bedrock state `gloamingforest:p` with the Java property's values (`IntegerProperty` ranges,
  every constant of an `EnumProperty`'s enum). The import checks them against a hand-written golden
  (`tools/import/expected-states.json`) and against the values upstream's blockstate file uses.
- The first listed value of a state is its Bedrock default. Booleans list upstream's default first: `[false, true]`, or
  `[true, false]` where upstream's default is `true` (`registerDefaultState`, else Java's `StateDefinition.any()`, which
  makes an unset boolean `true`: trophies `powered`, `HugeMushroomBlock` faces, rope `y`, ...); the selftest
  `import.bool_defaults` checks in game that Bedrock 1.26.51 defaults such a state to `true`.
- Integer properties are listed as `[0, 1, ..., max]` (Bedrock reads an integer state by its position, so the list
  always starts at 0); the Java value equals the Bedrock value, and values below the Java minimum (for example
  `distance` 0, `candles` 0) are unused. An integer's Bedrock default is therefore `0`: where upstream's default differs,
  the column *Java default* lists upstream's value, and the owner sets it wherever upstream uses `defaultBlockState()`
  (placement, world generation, structures).
- Enum values keep Java's names. The first value is the default state: upstream's default (`registerDefaultState`), else
  the conventional order of the shared vanilla names (`facing` north, `axis` y, ...), else Java's declaration order.
- `waterlogged` is not a block state on Bedrock (water is a separate liquid layer): it is dropped.
- No placement traits (`minecraft:placement_direction` / `placement_position`) are used: the families kit (F11)
  and the owning units set the states on placement, exactly as upstream's `getStateForPlacement`.
- Source `blockstate`: the property appears in upstream's blockstate file; `class`: only the Java class declares it
  (block entity renderers, vanilla bases such as `LeavesBlock`: `distance`, `persistent`).
